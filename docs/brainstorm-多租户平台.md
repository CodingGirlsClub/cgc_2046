# CGC 平台头脑风暴 — 多租户 · Agent · 插件化

> 日期:2026-07-31
> 状态:第一轮脑洞,待继续收敛

---

## 0. 概念澄清(用户确认)

- **CGC(Coding Girls Club)= 平台全称**,不是租户
- **Workspace(Club/空间)= 租户**:CGC 北京、CGC 深圳、CGC 北京的某书店,各自独立
- **Agent 是第一等公民**,且存在两种形态,需设计
- 角色(组织者/教练/学员等)都可能使用 Agent

---

## 1. 产品模型(理解到的机会)

### 1.1 层次结构

```
平台层 CGC
├── 认证(跨租户账号)
├── 租户注册/管理
├── 插件市场(Event/Course/支付…)
└── 公共资产模板(课程/活动模板)

租户层 Workspace(CGC 北京 / CGC 深圳 / …)
├── 核心成员(长期组织活动)
├── 角色(Owner/Admin/Tutor/Volunteer/Learner…)
├── Workflow(多个,按需)
├── Agent(个人分身 + 空间公共)
└── 插件挂载(可用可不用)
```

### 1.2 核心玩法闭环

```
新 Club 注册 → 初始化角色+模板 → 成员加入选角色
→ 组织者发起活动 Workflow → 角色/Agent 按流程协作
→ 活动落地(Event 插件) → 学习( Course 插件) → 作品沉淀(Portfolio)
```

## 2. Agent 身份模型(核心议题)

### 2.1 两种形态并存

| 形态 | 说明 | 例子 | 归属 |
|---|---|---|---|
| **个人 Agent(角色分身)** | 绑定用户身份,代表该用户执行 | 教练的"教学 Agent"、组织者的"筹划 Agent" | 用户 ↔ 角色 |
| **空间公共 Agent** | 基于 Workflow 协作需求存在,空间级共享 | "活动筹备 Agent"(组织者+志愿者共用) | Workspace |

### 2.2 权限分级

- Agent 和 Workflow 都要有**可见性/可用性**策略
- 例:某些 Agent/Workflow 仅 Owner/Admin/Tutor 可用,Learner/普通成员不可用
- 需要一张"谁能用哪个 Agent / 哪个 Workflow"的权限矩阵

### 2.3 待讨论问题

- 个人 Agent 在 Workspace 内可见吗?还是仅本人可见?
- 公共 Agent 由谁创建/授权?创建者可指定使用角色范围?
- Agent 的执行记录(日志)归谁?租户内可审计?

## 3. 三视角脑洞

### 3.1 Product Manager(市场/价值/竞争)

1. **租户一键初始化**:新 Club 注册时选择"活动型/学习型/混合型"模板,自动生成默认角色集 + 活动筹备 Workflow + 插件推荐——让 CGC 分会快速复制
2. **插件市场**:Event/Course/支付/报名/统计插件可插拔,平台侧做插件分发与质量审核(未来商业化出口)
3. **跨租户共享资产**:课程模板、活动 SOP、Workflow 模板在平台层沉淀,任何 Club 可一键复制——"一个城市的经验,全平台复用"
4. **成员成长体系**:Learner → Volunteer → Tutor → Admin 的晋升路径,让用户从参与者变成组织者(社区运营飞轮)
5. **活动全生命周期闭环**:筹划(Workflow)→ 招募(Event)→ 执行(签到/分工)→ 复盘(数据/作品),一个 Club 的完整运营循环,可量化产出

### 3.2 Product Designer(体验/上手/参与)

1. **空间品牌感**:每个 Workspace 独立主页——Logo、主题色、文案,进来就知道自己在"CGC 北京"还是"CGC 深圳"
2. **Agent 拟人化**:Agent 有头像/名字/状态(在线/执行中/空闲),像团队成员一样出现在协作界面——降低"和 AI 协作"的陌生感
3. **权限可视化仪表盘**:"谁能用哪个 Agent/Workflow"一屏看清,Owner 拖拽即可调整,不用懂权限术语
4. **加入 Club 流程**:邀请链接/二维码 → 选择角色 → 看到"我的 Agent 和我能做的第一件事"——从注册到第一次使用 < 2 分钟
5. **协作时间线**:活动筹备像项目时间线,显示"谁在哪个 Workflow 第几步、卡在哪",组织者一眼掌握进度

### 3.3 Software Engineer(技术/API/平台能力)

1. **多租户技术方案**:租户隔离策略——共享表 + tenant_id(起步)vs 每租户独立 schema(重隔离);Ash 原生 multitenancy 支持
2. **Agent 统一运行时抽象**:Agent 定义(身份/角色/权限)+ 执行器(对接 OpenClacky API),个人 Agent 和公共 Agent 同一模型,靠 policy 区分
3. **插件 SDK**:定义插件接口(资源声明 + 迁移 + 权限 + 前端组件),插件动态挂载到 Workspace,平台按插件协议分发
4. **权限引擎**:RBAC(角色→资源)+ Ash Policy(细粒度策略),策略集中管理、可测试
5. **审计与事件溯源**:Workspace 内关键操作(谁创建了 Agent、谁改了 Workflow、谁执行了)留痕,支持租户级审计

## 4. Top 5 优先级

### #1 多租户数据模型(地基)
- **内容**:Workspace(租户)+ 成员 + 角色,数据按租户隔离
- **理由**:一切功能的前提,不先定隔离边界,后面全要返工
- **假设**:起步期"共享表 + tenant_id"足够,不需要每租户独立数据库

### #2 Agent 双形态 + 权限模型
- **内容**:个人 Agent 与公共 Agent 统一建模,叠加角色权限策略
- **理由**:用户明确的核心诉求,决定产品差异化
- **假设**:权限分级用"角色级别"即可覆盖,不需要按单个用户细配

### #3 租户模板 / 快速初始化
- **内容**:新 Club 一键生成角色 + Workflow 模板 + 插件
- **理由**:决定平台能否从"一个 CGC"复制到"N 个 CGC"
- **假设**:模板可复制是分会冷启动的刚需

### #4 活动全生命周期 Workflow
- **内容**:筹划 → 招募 → 执行 → 复盘 的完整 Workflow + Event 插件
- **理由**:核心价值场景(线下活动是 CGC 的根)
- **假设**:组织者最痛的环节是"筹备协作混乱",Workflow 能解决

### #5 插件架构
- **内容**:Event/Course 先插件化,留插件协议
- **理由**:决定未来扩展(支付、报名、统计)而不推翻重来
- **假设**:插件抽象的成本可控,不会拖慢第一版
