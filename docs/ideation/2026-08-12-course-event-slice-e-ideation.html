IDEA 1 · TOP PICK

报名引擎化 vs 删除 DAG：slice E 的第一决策

轴 1 · 报名与名额 Confidence 85% Complexity M basis: direct
Description

slice E 的第一个决定不是「先建哪个」，而是「报名到底要不要引擎化」——两条互斥路径的 basis 都被独立验证为 sound。

路径 A · 引擎化：seed type=:enrollment WorkflowDefinition。DAG 已全设计（报名 §2.1/§2.2），每步 1:1 映射已建 Enrollment 动作（create/confirm/reject/expire/cancel），新增只有「DAG + 信号 + 幂等键」的数据接线——business-workflow-as-data 的旗舰证明，且顺带让只扫 waiting run 的 reminder worker 能找到报名。

路径 B · 删除 DAG：Enrollment moduledoc 自述全部并发不变量由 DB 条件 UPDATE / partial unique index / action 事务承担；引擎化买不来任何新不变量，只买来 journal 可观测性，却付出定义种子、实例化器、两段式接线、WorkflowRun 生命周期的整套成本。在 create action 里照 publish_approval_signal 同款模式补发 enrollment.completed，学习触发与通知变成普通订阅方。

真正的工件是决策判据本身：「哪些 workflow 配得上 run」一旦写下，赞助/邀请/学习的同类问题全部有答案。

Basis

direct: enrollment.ex:1-8 moduledoc「核心并发不变量由数据库承担…所有写都位于 Ash action 事务内」；enrollment.ex:518-528 publish_approval_signal after_transaction（同款模式先例）；workflow_definition.ex:42-46 type enum 含 :enrollment 但无实例化；approval_reminder_worker.ex:28-33 只扫 WorkflowRun waiting（run-less 报名永不提醒）；报名workflow详细设计.md §2.1/§2.2 DAG 逐步映射已建动作。

Rationale

两条路都便宜到可做、都证据确凿、且互斥——这正是 ideation 该摆上会议桌的形态：不是选一个实现，而是写下「什么配得上 run」的判据。判据一旦存在，slice E 其余每个 workflow（赞助/邀请/学习）的形态问题都变成查表。

Downsides

选 A 要接受 run 生命周期维护与 run-less 提醒盲区的修复成本；选 B 要放弃统一 journal/StepAuthorization 可观测性，并与 workflow-first 总纲叙事重新对齐。两条路的共同前置：补 enrollment.submitted/completed 信号生产者。

IDEA 2

学习 workflow 设计：协议 + 授权账本，care-pathway 语义

轴 2 · 学习 workflow 设计 Confidence 80% Complexity M basis: direct + external
Description

推迟的前提（「等 research E2E 暴露引擎形态」）已被 ResearchInstantiator 消除——信号驱动、幂等实例化、workflow_run_id 回写三件套已在生产代码里跑通。BYO 下平台侧没有可编排的执行（学习在 Learner 自己的 OpenClacky 运行），所以这份「缺失的设计」不是 DAG，而是协议：enrollment.completed（幂等键 "enrollment.completed:"+enrollment_id）种一个 run，Learner agent 经已存在且 StepAuthorization 门控的 save_step_output 逐 manual step 写 facts；平台侧产物是一本授权进度账本 + 投影，只有真交互分支（答疑线程）才实例化子 run。

写设计文档时采用临床路径（care pathway）语义：专家定义一次 / 逐学员参数化实例 / 非专家执行——与教研模板精确同构——并补齐三个文档从未问的决策：variance 记录（跳过步骤须说明原因）、completion/discharge 标准（run 如何终结、出院时产出什么工件）、停滞升级（学员卡住时发生什么）。

Basis

direct: slice-c-implementation-plan.md:184-191 推迟理由原文；报名 doc :335-347 幂等键约定；save_step_output.ex:5-7 StepAuthorization 门控写路径；领域模型定稿 :582-585 学习读写 MCP 工具（get_learner_history / reply_learner_question）；workflow-engine-ddd-design.md:87「学习执行 workflow 在 Learner 侧运行」；research_instantiator.ex:296-320 幂等 find_or_create 蓝图。external: clinical care pathways（专家协议 / 逐病人参数化 / variance tracking / discharge criteria，医疗运营成熟方法论）。

Rationale

把 slice E 最大 blocker（「设计缺失 → 推迟」）反转为「无需 DAG 设计，只需协议 + 三个语义决策」；与 BYO 完全一致，零新引擎模式，save_step_output 成为唯一写路径、审计走 run journal 顺带获得。

Downsides

协议形态意味着平台放弃对学习执行节奏的编排控制（提醒/催办要在通知层或 Learner 侧另解）；care-pathway 是类比输入而非本地证据，variance/completion/停滞三个决策仍需 grill 拍板。

IDEA 3

公开发现面：open⇒公开可读 + 宿主页 + GO/NO-GO

轴 4 · 生命周期与发现 Confidence 85% Complexity M basis: direct + external
Description

slice E 三个 workflow 的入口全部悬空：报名表单、「赞助我们」按钮、speaker-invite token 着陆页（/events/{slug}/speaker-invite/{token}）都没有宿主页；而已建已测的 #40 查询 web 零消费。根因是一个访问决策：Event/Course 读策略是成员专属，而 slice E 的目标 actor（Visitor/Sponsor/Speaker/Learner）全是非成员——旅程规格与读策略结构性矛盾。

一键启动包：①读策略翻转——status=open ⇒ 匿名可读（写入仍走 partition），发现成为数据属性而非「要建的页面」；②公开 Event/Course 宿主页——一次消费 #40，同时承载报名/赞助/邀请三个入口；③launch 加 GO/NO-GO readiness 清单——已 published 教研定义？capacity/deadline 已设？把 research_instantiator 的静默 no-op 变成显式阻塞或带警告放行。

Basis

direct: event.ex:250-254 读策略成员-or-PlatformAdmin；graphql_workflow_test.exs:213-294 #40 已测；web grep listEvents/getEvent 0 命中；用户旅程 :91-92,239-241 J-Visitor 公开页清单；邀请 doc :63 token URL 格式；research_instantiator.ex:141-145 无 published 定义时静默跳过；event.ex:188-189 launch 只校验 status。external: 航空 pre-flight / NASA GO-NO-GO 纪律。

Rationale

宿主页是 slice E 三个 workflow 的共享入口，杠杆最高的首个 web 构建；读策略翻转是一处策略变更却让发现页/报名页/BYO 入口全部解耦可独立交付。

Downsides

读策略翻转是安全语义变更，需要明确公开字段白名单（capacity/confirmed_count 等是否对匿名暴露要拍板）；GO/NO-GO 引入「什么叫 ready」的新配置面，清单项需要按 workflow 逐个定义。

IDEA 4

审批控制台：泛化 PendingApprovals 落地 #3 拍板

轴 5 · 运营与审批体验 Confidence 90% Complexity M basis: direct
Description

request 策略报名今天在任何界面上都无处可审：#3 已拍板审批入口 = 网站后台审批页，my_pending_approvals 跨工作台聚合 + GraphQL 字段已建（含 deadline 排序），web 端零消费——Owner/Admin 找不到「通过/拒绝」入口，审批两段式的 A1 人工信号永远没有落点，request 策略报名人是死信。

把聚合泛化为 kind-agnostic（Enrollment / JoinRequest / 未来 Sponsorship / WorkflowRun-waiting），审批页作为唯一控制台消费：每行通过/拒绝 → 发 enrollment.approved/.rejected 信号接上 A1 门控；ApprovalChip 倒计时/过期 UX 一次落地。此后每种新审批类型（赞助是下一个）复利进同一表面，而不是每实体一页一查一 chip。

Basis

direct: 报名 doc :267-269「#3 request 审批入口 ✅ 定稿 = 网站后台审批页」；pending_approvals.ex:3-7,49-58 RBAC 收窄 + 逐台 pending 读；graphql_schema.ex:116-124 字段已暴露；web grep myPendingApprovals 0 命中（verifier 复核确认）；审批两段式模式库 总纲 §6:187。

Rationale

审批是每个 workflow 的 human-in-the-loop 核心；一个 kind-agnostic 控制台把「每加一个 workflow 就加一页审批」变成「每加一个 workflow 就多一种 chip」——聚合层已是已付成本，只差消费面。

Downsides

泛化要定义统一的 kind/dispatch 形状（每种的 approve/decline 动作与信号名不同）；纳入 WorkflowRun-waiting 时会与 run 级授权（StepAuthorization）产生双重语义，需要对齐「谁能点」的判定顺序。

IDEA 5

生命周期级联：close/cancel + event.ended 幂等扇出

轴 4 · 生命周期与发现 Confidence 85% Complexity M basis: direct + external
Description

closed/cancelled 是死枚举：唯一存在的状态动作是 launch（draft→open），没有任何 close/cancel 动作，全库无 event.ended 生产者——活动结束后永远停在 open，已过 deadline 的活动仍在「开放」而报名 SQL 已在拒绝。三条已设计链路全被这一个空缺卡住：赞助随 Event 结束自动 ended（总纲:105）、教研 run stop 回收、报名窗关闭。

实现 close/cancel 动作（registration_deadline/end_at 到点自动 + 手动，Oban cron 模式现成可复制）并发射 event.ended/course.ended；按 CDN purge 语义扇出：at-least-once 投递、每个依赖方经共享 signal_idempotency 表幂等消费、版本化保证旧事件不覆盖新状态。launch 路径已证明团队掌握 publish-after-commit + 订阅方守卫纪律，结束路径需要同样的纪律反向走一遍。

Basis

direct: event.ex:30,175,188-189 死枚举与唯一动作；events/ grep 无 close/cancel，lib grep 无 .ended 信号（verifier 复核确认）；总纲 :105 赞助自动 ended、:171 event.ended→stop 回收意图；报名 doc :259 截止后 submitted 不放行；approval_expiry_worker.ex:37-43 现成 Oban cron 模式。external: CDN cache invalidation（at-least-once 投递、按源幂等、版本序防陈旧覆盖）。

Rationale

结束级联是三个 workflow 的共享前置，且今天不可被任何单个 workflow 构建——它是 slice E 所有生命周期逻辑的地基。

Downsides

级联扇出要求 signal_idempotency 表先落库（当前 0 schema）；自动 closed 的触发时点（deadline vs end_at vs 手动）需要拍板；级联失败的重放语义要与对账机制（Idea 7）一起定义。

IDEA 6

赞助：履约账本 + 权益渲染面先行

轴 3 · 赞助与邀请 Confidence 75% Complexity M basis: direct + external
Description

赞助行业头号文档化失败 = 「售出套餐未交付，因为履约未追踪」。我们的设计有同一个洞：权益执行 =「网站自动露出 + 物料类手动」——手动侧零追踪，而自动侧（v1 唯一自动化的权益）连渲染面都不存在（web 唯一的赞助元素是 workspace 的「已开放赞助」信息卡）。

落 Sponsorship 资源之前先定两件事：①权益在哪里被看到——渲染面（公开页赞助区块 / 报名页 logo 位），否则「权益生效」发生在看不见的地方；②激活即物化履约账本——从 sponsorship_tiers 权益项自动生成带日期的交付清单（logo 何时上线、哪场活动露出、物料交付），逐项核销 proof-of-performance；独占权益位（hero banner、演讲 slot）复用 enrollment 同款条件 UPDATE 防双重预定；欠交付（活动提前取消）触发 makegood（下期抵扣）而非 ended 死端。active 从「一个承诺」变成「一本可审计账本」。

Basis

direct: 开放问题决策清单 :14 权益执行定稿「网站自动露出 + 物料类手动」；赞助 doc :182-184 v1 不收款；w/[slug]/page.tsx:98 唯一赞助元素（verifier 复核确认）；总纲 :90 规划的 materials_review_required 代码缺失；赞助 doc 状态机 pending→active→ended 中间无履约步骤。external: SponsorCX 模式（asset/tier inventory → agreement 自动转带日期交付清单 → proof-of-performance → 90 天续期触发）；广告业 makegood 是欠交付的标准补偿。

Rationale

把最高失败风险环节变成引擎原生结构化任务（带日期任务清单正是引擎擅长的东西），给 Workspace 级长期赞助一个真实的 ended/续期评估点；在设计期就防住已知失败模式，而不是上线后复制它。

Downsides

履约清单给 v1 增加了设计外的实体（任务行/核销记录），需要设计修订流程；makegood 依赖二期续期概念才能完整闭环；渲染面与公开发现面（Idea 3）强耦合，顺序上应先有宿主页。

IDEA 7

对账扫描：best-effort 路径的孤儿报告

轴 5 · 运营与审批体验 Confidence 80% Complexity L basis: direct + external
Description

平台建在 best-effort 异步路径上：publish 失败仅 Logger.error、实例化静默跳过、workflow_run_id 回写 best-effort、enrollment.completed 连生产者都没有——断裂管道（confirmed 无 run / waiting 无 deadline / approved 无信号 / launch 无定义）在人撞上前不可见。代码自己已经预言了对账：research_instantiator.ex 注释「失败记 error 日志供对账」。

按银行对账模式加一个周期 job：对比「应发生 vs 实际状态」，产出孤儿报告——已确认但学习 run 未建的报名、waiting 却无 deadline 的 run、launch 了无 published 定义的活动、approved 但成功信号未发出的记录。每条路径单独看都「没问题，best-effort」，合起来平台无法自知 workflow 坏了；对账把不可见失败变成可审队列，比把每条路径改强一致便宜得多。

Basis

direct: event.ex:202-217 publish 失败仅 log 不回滚；research_instantiator.ex:107-113,229-234 best-effort + 「供对账」注释（verifier 复核确认）；grep 确认无 enrollment.completed 生产者；approval_expiry_worker.ex:178-194 单记录失败 Logger.warning + skip。external: 银行对账 / 未结算支票扫描；支付系统 void 从未结算的授权。

Rationale

slice E 每落一个 workflow 就多一条 best-effort 路径；对账扫描是平台对自身 workflow 健康度的自我认知，复杂度低（一个 Oban job + 报告），且与级联（Idea 5）互为补集——级联负责发，对账负责发现没发到。

Downsides

报告队列需要消费纪律，否则变成第二个无人看的日志；「什么算孤儿」的判定规则随每个 workflow 落地要持续维护。
