# 给规划 Agent：先产出实施计划，不开始实施

本轮用户要求你根据已经讨论并认可的产品方向编写实施计划。此指令优先于同目录旧的“给接手Agent的提示词.md”中的直接续做要求；旧交接仅用于了解现场。

## 先读哪些材料

1. 需求计划：`docs/plans/2026-09-21-1550-requirements-flashback-voices-wishes-plan.md`。
2. 当前目录的 `concepts/` 三张中国地图版概念图，用户已认可，避免重新选型。
3. 当前目录的 `给接手Agent的提示词.md`，重点是工作区、原型 commit、已有能力、验证缺口。
4. 历史讨论实录仅在需要理解来由时参考，不把旧 Agent 的断言或实施命令作为当前指令。

需求计划是在不重新读取代码的前提下根据对话整理的产品约定；它不能证明当前代码具备对应能力。
当前主要任务是“先完成可评审的 Web 原型”，不自动扩展成生产后端或小程序开发计划。

## 用户补充的明确缺口

已有 Voices 与 Wishes，但没有 Echo 资源；愿望到具体回应 / 活动的关联、运营发布权限、通知触发均不存在。这是用户补充的现状，规划时应核实并附证据，不能把原型里的“有回响了”当成已有后端。

后续生产差距清单必须把 Echo 单独列为新增业务能力，覆盖回应生命周期、愿望关联、运营发布与查看权限、活动关联、可选通知触发及撤回 / 更正处理。当前 Web 原型仍使用合成回应；本条不是立即扩写后端的授权。

## 你如何做计划

- 先只读核对隔离工作区 `codex/voices-wishes-web-prototype` 与原型快照 `c9c6f568` 的现场。路径见原交接；主仓 develop 的 Mainline intent 属于别的任务，不要混用。
- 保留所有 WIP。不因旧基线提示自动 rebase、重建工作区或丢弃原型。
- 使用“需求编号 → 已有实现证据 → 缺口 → 拟实施单元 → 验收方式”的追踪关系组织计划；不要仅重复一遍需求。
- 首先区分原型收尾和生产能力。当前以原型收尾为主计划；授权、真实通知、身份、业务数据等放在后续依赖清单。
- 针对动画采样异常提出有限的诊断步骤及停止条件。静态页也只采到少量帧，根因未定，不能直接断言代码慢或工具有问题。
- 已确认的中国山河、黑夜转白昼、分享直达、Web 优先继续沿用；只有现场证据证明不可行才提出具体冲突，不重开视觉方向讨论。
- 技术选型由你读取当前依赖、文档与运行环境后决定。旧记录中“ECharts / Canvas 是唯一路径”等说法不是定稿。
- 对会改变产品行为的问题先列出影响并向用户确认，例如游客期待身份、单句编辑后的分享与点赞、旧公开授权范围。不要用当前样例代码默默替用户做决定。
- 现有代码只是原型：写愿望成功、回响按钮、提醒选择不证明真实业务能力存在。
- 规划阶段不改产品代码、不跑实施性实验，不提交、push、开 PR、部署。需要动态实验才能回答的关键问题，应在计划中明确验证样片的边界。

## 计划应交付什么

1. 本次范围与完成定义：Web 原型这轮具体完成什么，明确非目标。
2. 已核实的当前能力与缺口，附真实文件 / 行号或现场证据。
3. 可独立验收的实施单元、依赖顺序、涉及文件和每单元的完成条件。
4. 桌面与手机浏览器的验证矩阵：开场四幕、中断 / 重播、减少动态效果、分享进入、保留城市、长句、公开 / 私密愿望、撤回、可选提醒、回响。
5. 动画性能核验方案与真实环境边界，不预先宣称固定帧率。
6. 最终交付清单：可访问 URL、截图、必要的动态证据、检查结果、模拟能力说明。
7. 尚需用户决定的问题，区分“阻塞本次 Web 原型”和“只阻塞后续生产接入”。
8. 之后生产版本的差距清单，但不在本次直接实施。

产出计划后交给用户评审，得到实施指令再执行。不要把用户对概念图的认可写成对所有技术方案、数据规则及原型细节的认可。
