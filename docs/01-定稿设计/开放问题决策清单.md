### 赞助-#1：赞助数量/档位限制（Sponsorship Tier 限量？）

**一句话问题**：赞助方数量是否限制、赞助档位是否限量（如"冠名档唯一"）？

**现状**：设计默认**不限制赞助方数量**（无并发扣减，赞助 #9 已定稿幂等点不含名额扣减）；建模建议"若需冠名档唯一 → tier 配置上限（active 计数 < tier.limit，A3 事务内校验，同报名名额扣减机制）"，是否限制待 grill。**隐含倾向：v1 不限额、档位仅定义**。

**可选方案**：
- **方案 A（推荐）**：v1 不限制数量；tier 仅定义档位（名称/金额/权益项），`tier.limit` 字段**预留但 v1 不启用校验**；二期启用时走报名名额扣减同一套机制（active 计数 + 原子扣减 + 幂等）。
  - 影响：领域模型 SPONSORSHIP_TIER 预留 `limit` 字段（可空，null = 不限）；引擎无改动；接口无改动。
  - 工作量：低（仅加一个可空字段）。
  - 风险：低。权益未定（赞助-#3）前限量无业务意义；一期不限额避免误伤。
- **方案 B**：v1 即支持 tier.limit（A3 事务内校验 active < limit，同名额扣减）。
  - 影响：引擎复用报名扣减模式；领域模型 SPONSORSHIP_TIER.limit 必填校验；接口 A3 加校验逻辑。
  - 工作量：中（复刻报名配额机制）。
  - 风险：中。权益清单未定，档位稀缺性未定，限量规则可能返工。
- **方案 C**：按 Workspace 配置是否限量（开关 + limit）。
  - 影响：多一层配置；领域模型 Workspace 配置项。
  - 工作量：中高。
  - 风险：中高。过度设计，二期再配不迟。

**推荐：方案 A**。理由：赞助 v1 不收款（赞助 #2 定稿）、权益未定，数量限制依赖权益稀缺性，一期不限额成本最低且不阻塞；`tier.limit` 预留字段保证二期可平滑启用（复用已验证的报名配额机制）。

**影响面**：`docs/01-定稿设计/赞助workflow详细设计.md`（§3.3 资金边界/§5 Sponsorship 字段草案）、`docs/01-定稿设计/领域模型定稿.md`（§5.1 SPONSORSHIP_TIER 行补 limit 字段说明）。

### 赞助-#3：权益清单（赞助换什么）

**一句话问题**：赞助权益具体包含哪些项（logo 展示位/文案/报名页露出/现场物料…）？

**现状**：设计建模建议"权益内容由 Workspace 配置 `sponsorship_tiers` 驱动；具体权益项待 grill"。workflow 只登记 `tier_id + amount`（v1 不收款），权益执行属网站展示/物料制作。**隐含倾向：权益 = Workspace 配置数据，非 workflow 核心逻辑**。

**可选方案**：
- **方案 A（推荐）**：Workspace 配置 `sponsorship_tiers`（tier 名称/金额/权益项列表，权益项从平台预定义集勾选：logo 展示位、报名页露出、鸣谢页、现场物料位）；Sponsorship 记录关联 `tier_id`；v1 权益执行 = 网站自动露出（logo/报名页/鸣谢页）+ 物料类权益由 Owner 手动执行（审批通过后人工安排）。
  - 影响：领域模型新增 SPONSORSHIP_TIER 实体（Workspace 级配置）+ SPONSORSHIP.tier_id；网站配置页 + 报名页露出；workflow 无改动（tier_id 作为 P1 输入）。
  - 工作量：中（配置页 + 露出展示）。
  - 风险：低。权益执行拆分清晰（自动露出 vs 手动物料），不阻塞 workflow。
- **方案 B**：平台固定最小权益集（v1 固定 logo + 报名页露出 + 鸣谢页），Workspace 不可配。
  - 影响：领域模型仅 SPONSORSHIP.tier_name/amount 文本；网站固定展示。
  - 工作量：低。
  - 风险：中低。灵活度差，不同 Workspace 权益诉求无法满足，二期仍要配置化。
- **方案 C**：v1 只登记 Sponsorship 记录，权益执行完全手动（网站不自动露出）。
  - 影响：领域模型 SPONSORSHIP 无 tier 关联；网站不新增露出。
  - 工作量：最低。
  - 风险：中高。赞助"权益生效"形同虚设，Sponsor 体验差，违背 workflow 目标（权益生效为审批后核心产物）。

**推荐：方案 A**。理由：权益清单本质是 Workspace 运营配置而非 workflow 逻辑，配置化成本可控；自动露出（logo/报名页）兑现"审批通过 → 权益生效"闭环，物料类手动符合 v1 不收款、轻量交付的边界；为二期收款/限量留好 tier 载体。

**影响面**：`docs/01-定稿设计/赞助workflow详细设计.md`（§3.3 资金边界补权益执行说明、§5 Sponsorship 字段草案）、`docs/01-定稿设计/领域模型定稿.md`（§5.1 新增 SPONSORSHIP_TIER）、`docs/01-定稿设计/用户旅程与Web功能清单.md`（J-Sponsor 权益呈现）、网站（Workspace 配置页、报名页露出）。

### 赞助-#4：Workspace 级赞助审批是否加严

**一句话问题**：Workspace 级（长期）赞助的审批人是否要比 Event 级更高级别？

**现状**：设计建模建议 Owner/Admin（与 Event 级同权限）；"长期承诺可配仅 Owner 审批或需平台 Admin 备案"。**隐含倾向：与 Event 级同权限（Owner/Admin），加严是可选配置**。

**可选方案**：
- **方案 A（推荐）**：**Workspace 级仅 Owner 审批**；Event 级 Owner/Admin 均可审；平台 Admin 备案二期。
  - 影响：授权校验（A3 审批 StepRole 按 level 区分：event→[Owner,Admin]，workspace→[Owner]）；领域模型 SPONSORSHIP.approved_by 校验规则；无引擎改动。
  - 工作量：低（审批人角色校验规则差异）。
  - 风险：低。Workspace 级长期承诺影响整个 Workspace 资源（报名页长期露出），加严到 Owner 合理且成本极低。
- **方案 B**：与 Event 级同权限（Owner/Admin 均审，当前设计默认）。
  - 影响：无额外改动。
  - 工作量：最低。
  - 风险：中低。Admin 可能仅是协作角色却可批准长期赞助，权限语义略宽；但若团队认可 Admin 权限则可行。
- **方案 C**：Workspace 级需平台 Admin 备案（跨租户流程）。
  - 影响：新增平台 Admin 审批步骤（第三个人工信号 → 赞助 workflow 需三段审批：意向审批 + 权益审批 + 平台备案）；领域模型新增备案状态。
  - 工作量：高（跨租户流程 + 三段审批）。
  - 风险：中高。跨租户审批违背 v1 平台自治边界（partition 归属 Workspace），成本高收益低。

**推荐：方案 A**。理由：Workspace 级是长期承诺，仅 Owner 审批语义更准（与报名审批 Owner/Admin 同级、但赞助长期性加严一级）；成本仅审批人校验差异；平台备案涉跨租户，二期再议。

**影响面**：`docs/01-定稿设计/赞助workflow详细设计.md`（§1.2 两级审批权限、§3.4 审批页）、`docs/01-定稿设计/领域模型定稿.md`（§3 授权矩阵/§5.1 SPONSORSHIP.approved_by）、`docs/授权与数据边界.md`（若有，审批角色矩阵）。

### 邀请-#1：Speaker 是否必须全局账号

**一句话问题**：被邀请的 Speaker 是否必须注册/登录全局账号才能接受邀请？

**现状**：设计建模建议"需要全局账号（接受时注册/登录，与 Sponsor 对齐：材料产出归属/审计/互动）；不成为 Workspace 成员"；J-Speaker 未明确。**隐含倾向：必须全局账号**。

**可选方案**：
- **方案 A（推荐）**：必须全局账号——接受邀请时注册/登录（或已有账号直接登录），`accepted_by` 关联账号；不自动成为 Workspace 成员。
  - 影响：邀请 workflow 接受分支加"登录/注册"前置约束（S2 前）；领域模型 SPEAKER_INVITATION.accepted_by → 账号 FK；授权无新增（Speaker 仅 Event 级）。
  - 工作量：低（复用注册/登录模块，与 Sponsor #6 定稿同路径）。
  - 风险：低。与 Sponsor 已定稿语义对齐，材料产出归属/审计有账号载体。
- **方案 B**：不强制账号，匿名/邮件确认后接受（token 关联身份，材料产出归属弱）。
  - 影响：领域模型 accepted_by 允许 null/邮箱；审计归属弱；产出落点无法关联账号。
  - 工作量：低。
  - 风险：中高。分享材料公开/半公开，无账号则无法审计、无法互动（答疑/复盘），与平台账号体系割裂。
- **方案 C**：必须账号但支持"仅此活动轻量身份"（免密码临时身份，二期）。
  - 影响：新增轻量身份机制。
  - 工作量：高。
  - 风险：高。引入新身份体系，一期不值得。

**推荐：方案 A**。理由：与 Sponsor 账号决策（赞助 #6 已定稿"需全局账号、不成为成员"）完全对齐；材料产出归属、审计、互动都需要账号；成本仅复用注册/登录。

**影响面**：`docs/01-定稿设计/邀请workflow详细设计.md`（§1.1 谁参与、§3.1 接受分支加登录约束）、`docs/01-定稿设计/用户旅程与Web功能清单.md`（J-Speaker 接受流程）、`docs/01-定稿设计/领域模型定稿.md`（§5.1 SPEAKER_INVITATION.accepted_by）。

### 邀请-#4：接受邀请后是否拆独立分享 workflow

**一句话问题**：Speaker 接受邀请后的分享材料产出流程，是否单独建一个 workflow？

**现状**：设计建模建议"v1 不拆——材料产出为邀请 workflow 内步骤（M1，Step facts 落点）；未来分享流程复杂（彩排/答疑/复盘）再拆，由 `speaker.accepted` 信号触发（同 enrollment.completed 触发模式）"。**隐含倾向：v1 不拆**。

**可选方案**：
- **方案 A（推荐）**：v1 不拆——M1（材料产出）为邀请 workflow 内步骤；预留 `speaker.accepted` 信号触发扩展点，二期分享复杂化时再拆。
  - 影响：维持邀请 workflow 单 run（邀请段→决策段→产出段）；无新定义；无引擎改动。
  - 工作量：无新增。
  - 风险：低。v1 分享 = 一次材料产出（人工步骤 + facts），独立 workflow 无收益。
- **方案 B**：v1 即拆独立分享 workflow（接受后自动触发新 run：材料产出 + 未来彩排/答疑/复盘）。
  - 影响：新增分享 workflow 定义 + `speaker.accepted` 订阅触发；领域模型新增分享 run 关联。
  - 工作量：中高（多一套定义/生命周期/权限面）。
  - 风险：中高。v1 分享仅材料产出，独立 workflow 空转成本高。
- **方案 C**：半拆——接受后自动建"分享 run"但仅含材料产出步骤（为未来扩展预留 run 结构）。
  - 影响：新增轻量分享定义 + 触发。
  - 工作量：中。
  - 风险：中。提前引入 run 结构，但内容与邀请 workflow 重复（M1 移到新 run），v1 反而多一跳。

**推荐：方案 A**。理由：v1 分享场景单一（材料产出），内嵌成本最低；`speaker.accepted` 触发模式已被验证（enrollment.completed 模式），二期拆分享 workflow 平滑、无返工。

**影响面**：`docs/01-定稿设计/邀请workflow详细设计.md`（§2.1 DAG 明确 M1 内嵌、§4.2 触发扩展点说明）、（二期）新增分享 workflow 定义文档。

### 教研-#2：材料交付形式 + 是否启用审核入口

**一句话问题**：教研材料（大纲/招募物料）以什么形式交付、是否启用审核（复用网站后台审批页）？

**现状**：设计建模建议"交付形式 = 用户侧 OpenClacky `save_step_output`（Step facts）+ 网站教研页可查；审核入口 = 复用网站后台审批页模式（pending 列表 + 通过/打回、打回重提、非 MCP 管理类、不复用 D8 确认流）——**是否启用审核（S5→S6）待 grill**"。**隐含倾向：交付形式定稿；审核默认不启用（materials_review_required 默认 false）、门控保留**。

**可选方案**：
- **方案 A（推荐）**：交付形式定稿（`save_step_output` + 网站教研页可查）；审核**默认关闭、可配置启用**——`materials_review_required` 默认 false，S5 门控直通 S7；Workspace 或 Event/Course 属性开启后走 S6 审核（复用网站后台审批页，通过/打回重提）。
  - 影响：教研 workflow 门控保持双路径（默认跳过/可启用）；领域模型 Event/Course 增 `materials_review_required` 属性；网站后台审批页（报名 §3.5 模式）新增"教研材料审核"入口，仅启用时可见。
  - 工作量：中（门控配置 + 审批页扩展；若默认关闭可后置实现审批页）。
  - 风险：低。Tutor/Volunteer 为 Workspace 成员（可信），默认免审合理；需要审核的 Workspace 可自行开启。
- **方案 B**：v1 强制启用审核（默认 true，所有教研材料需 Owner 审核）。
  - 影响：教研 workflow 总是走 S5→S6；领域模型属性默认 true；审批页必须 v1 实现。
  - 工作量：中高（审批页必须做）。
  - 风险：中。所有教研材料强制审批，Owner 负担重，与"教研材料是内部产物"定位不符（非对外承诺如赞助权益/报名准入）。
- **方案 C**：v1 不启用且不预留门控（S5/S6 从 DAG 移除，二期再加）。
  - 影响：教研 DAG 少两个节点；二期需重新设计 DAG 版本。
  - 工作量：最低。
  - 风险：中低。二期加审核要动 DAG 模板（教研已定"定义一次多实例"，模板改动影响面大），预留门控成本极低、更稳妥。

**推荐：方案 A**。理由：交付形式无争议（与邀请/赞助材料产出模式一致）；审核默认关闭符合"内部教研产物、成员可信"定位；门控双路径保留使二期启用零 DAG 改动（仅配置翻转），审批页复用报名 §3.5 已验证模式。

**影响面**：`docs/01-定稿设计/教研workflow详细设计.md`（S5/S6 门控说明、§3.3 审核入口）、`docs/01-定稿设计/领域模型定稿.md`（§5.1 Event/Course 增 `materials_review_required`）、`docs/01-定稿设计/报名workflow详细设计.md`（§3.5 审批页模式声明可复用性，无实质改动）。

### 教研-#3：现场辅导是否独立决策点

**一句话问题**：答疑循环中 Tutor 介入是否算独立决策点、是否需要人工确认、是否拆独立 workflow/run？

**现状**：设计建模建议"v1 现场辅导 = 同一 workflow 内 S8↔S9 循环（Workflow 层顺序等待 PASS）；答疑交互复杂/需独立权限边界时拆独立『答疑段』run/子 workflow（同 enrollment.completed 触发模式）"。**隐含倾向：v1 不拆独立 run；Tutor 介入为 workflow 内门控（自动应答置信度低转人工）**。

**可选方案**：
- **方案 A（推荐）**：v1 不拆独立 run——答疑为同 workflow 内 S8↔S9 循环；**Tutor 介入 = workflow 内门控决策点**（自动应答置信度低于阈值 / 学员点名 / 复杂问题 → 门控转人工步骤 `research.answer`，Tutor 在 OpenClacky 应答）；不要求每次答疑人工确认（自动应答为主、人工兜底）；判定规则 v1 细化（与教研 🟡 #8 关联）。
  - 影响：教研 DAG 保持 S8（含门控分支）→ S9；领域模型无新实体（门控规则属 workflow 内逻辑）；无引擎改动（Workflow 层顺序等待已 PASS）。
  - 工作量：低中（门控判定规则 v1 联调细化）。
  - 风险：低。与 Workflow 层验证能力匹配；Tutor 人工介入保留但非必经，体验好。
- **方案 B**：v1 拆独立「答疑段」run/子 workflow（`event.started` 触发独立答疑 run，结束后并入收尾）。
  - 影响：新增答疑定义/子 workflow；生命周期多一跳；领域模型新增答疑 run 关联。
  - 工作量：中高。
  - 风险：中高。v1 答疑交互量未知，提前拆 run 增加定义与生命周期成本；与教研"定义一次多实例"叠加复杂度上升。
- **方案 C**：每次答疑必须 Tutor 人工确认（全人工，不用自动应答）。
  - 影响：答疑全人工；领域模型/规则简单但交互重。
  - 工作量：低（无自动应答逻辑）。
  - 风险：中高。无自动应答则答疑段需要 Tutor 全程在线，人力成本高；与 J-Tutor"答疑 Agent"定位不符。

**推荐：方案 A**。理由：自动应答 + 人工兜底门控与 J-Tutor"答疑 Agent"定位一致；Workflow 层顺序等待能力已 PASS，无需为 v1 拆独立 run；判定规则（置信度阈值等）属 v1 细化项（教研 🟡 #8），可在联调期收敛，不阻塞设计定稿。

**影响面**：`docs/01-定稿设计/教研workflow详细设计.md`（S8 门控分支说明、S9 结束判断、§7 开放问题 #3 标记定稿）、`docs/01-定稿设计/领域模型定稿.md`（无新实体，可在 §5 备注答疑门控规则）、教研 🟡 #8（答疑判定规则 v1 细化项）。

## 三、推荐暂缓/二期项（2 项）

### 邀请-#3：候选池批量邀请（一次邀请多人）

**一句话问题**：是否支持演讲者候选池、一次批量邀请多人？

**现状**：设计建模建议"v1 逐人邀请（一个 Speaker = 一个 run）；候选池/批量邀请可复用 InviteBatch quota 机制扩展（报名 §3.6）"。**隐含倾向：v1 逐人，候选池二期扩展**。

**可选方案**：
- **方案 A（推荐）**：**二期再做**——v1 逐人邀请（Owner 逐个创建 SpeakerInvitation，一人一个 run）；二期候选池 = 批量创建多个邀请 + 批量 token 管理，复用 InviteBatch quota 机制（报名 §3.6 已验证：共享批次码/配额/原子扣减）。
  - 影响（二期）：邀请 workflow §3.3 扩展；网站批量邀请 UI；InviteBatch 复用（SpeakerInvitation 关联 batch_id）。
  - 工作量（二期）：中高。
  - 风险：低（v1 逐人已覆盖单 Speaker 核心场景；二期扩展点明确）。
- **方案 B**：v1 支持候选池（Owner 导入候选列表，一次生成 N 个邀请 run）。
  - 影响：邀请 workflow 实例化批量入口；领域模型 SPEAKER_INVITATION.batch_id；网站导入 UI。
  - 工作量：高（批量 UI + 批量实例化 + 去重）。
  - 风险：中高。v1 演讲者规模小，批量场景弱；提前投入回报低。
- **方案 C**：候选池 = 简单名单列表（不进 workflow，Owner 手动逐个发 token）。
  - 影响：网站名单 CRUD + 手动逐个创建邀请。
  - 工作量：低中。
  - 风险：中。绕过 workflow 的"名单"与 workflow 邀请两条数据源，语义割裂、易脏数据。

**推荐：方案 A（二期）**。理由：v1 核心场景是单个 Speaker 的邀请-接受-产出，逐人邀请已覆盖；批量邀请依赖批量 UI 与 InviteBatch 扩展，工作量与风险偏高，而 InviteBatch 复用点是现成扩展路径（报名 §3.6 已验证），二期平滑启用。

**影响面**：（二期）`docs/01-定稿设计/邀请workflow详细设计.md`（§3.3 候选池扩展）、`docs/01-定稿设计/报名workflow详细设计.md`（§3.6 InviteBatch 复用声明）、网站批量邀请 UI、领域模型 SPEAKER_INVITATION.batch_id。

### 邀请-#5：Workspace 级讲师 / 长期嘉宾

**一句话问题**：讲师（Speaker）是否可挂 Workspace 级（长期合作），而非仅 Event 级单次邀请？

**现状**：设计建模建议"本 workflow 仅 Event 级；Workspace 级长期讲师属成员/合作关系（另一议题，v1 不做）；是否需要单独『讲师关系 workflow』待 grill"。**隐含倾向：v1 仅 Event 级，Workspace 级属另一议题**。

**可选方案**：
- **方案 A（推荐）**：**二期再议**——v1 邀请 workflow 仅 Event 级（Speaker 为单次活动被邀请人，关系随 Event 结束）；Workspace 级长期讲师属成员/合作关系建模（与 Tutor 成员身份、Sponsor 非成员关系都不同），作为独立议题二期设计。
  - 影响（二期）：领域模型新增讲师关系实体/角色（如 WorkspaceSpeaker / SpeakerRelationship）；邀请 workflow 扩展 Workspace 级上下文；授权矩阵更新。
  - 工作量（二期）：高（关系建模 + 生命周期 + 权限）。
  - 风险：低（v1 不受影响；避免把两个不同关系语义揉进一个 workflow）。
- **方案 B**：v1 简单支持 Workspace 级 SpeakerInvitation（长期嘉宾挂 Workspace，可被多个 Event 复用）。
  - 影响：邀请 workflow 加 Workspace 级分支；领域模型 SPEAKER_INVITATION.workspace_id；生命周期（跨 Event）复杂化。
  - 工作量：高。
  - 风险：高。长期关系生命周期（启用/停用/到期）未建模，简单挂靠会造成状态空洞；与 Event 级单次语义混用易错。
- **方案 C**：v1 支持"讲师名片/资料库"（Workspace 维护讲师档案，邀请时从档案选人，不做长期关系）。
  - 影响：网站讲师档案 CRUD；邀请创建时引用档案。
  - 工作量：中。
  - 风险：中低。档案库是可选增强，但属"邀请 UX"非"关系建模"，可二期与候选池合并做。

**推荐：方案 A（二期）**。理由：Workspace 级长期讲师是"关系"建模（生命周期/权限/审计），与 Event 级单次邀请语义不同，v1 强行支持会造成状态与授权空洞；作为独立议题二期设计更干净；方案 C 的档案库可并入二期候选池（邀请-#3）一并做。

**影响面**：（二期）`docs/01-定稿设计/领域模型定稿.md`（新增讲师关系实体/角色）、`docs/01-定稿设计/邀请workflow详细设计.md`（Workspace 级扩展）、`docs/授权与数据边界.md`（讲师权限）、用户旅程 J-Speaker 扩展。
