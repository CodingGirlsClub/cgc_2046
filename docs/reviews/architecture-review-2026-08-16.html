A · 原子 claim 条件 UPDATE 家族收编 ApprovalClaim

Strong

Files（7 个资源 module 内联 ~14 份）

  • accounts/join_request.ex:175-213 · workspace_application.ex:180-208 （逐字同构）
  • accounts/invitation.ex:424-465,477-520 · user.ex:213-241
  • events/enrollment.ex:388-450,606-633 · sponsorship.ex:503-780 （含读回消歧，最完整）
  • events/speaker_invitation.ex:528-590,647-680
  • 对照：changes/transition.ex（第三套守卫约定，仅 workflow_run 用）

Problem

「在 Ash action 事务内原子抢占一行」是同一个 interface 想法，却没有任何 module 承载——每个资源各自内联 ~25 行裸 SQL + num_rows 判读 + 错误分支。守卫约定三套并存（裸 SQL claim / validate_pending_status 快照守卫两份逐字拷贝 / 声明式 Transition），错误 taxonomy 三套（字符串 / InvalidAttribute exception / 错误原子）。num_rows=0 的消歧（already_processed vs deadline_passed vs exclusive_slot_taken）只有 sponsorship 实现了读回版本。

Solution

抽一个深 module Cgc2046.Changes.ApprovalClaim：条件 UPDATE 构造器（表 + set 映射 + status 守卫 + deadline 守卫，列名知识复用 ApprovalDeadline.derive/1）+ num_rows 判读 + 统一错误 taxonomy + 可选读回消歧。资源 action 退化为：一行 claim + after_action 效果（admit_member、建 workspace、物化 SponsorshipDelivery）。

Benefits

  • Locality：TOCTOU 语义修一处 = 修 7 个资源；下一个 intake 资源（invite batch 运营面在热点上）不再产第 15 份拷贝
  • 测试面：并发抢占的表驱动契约测试 1 套，替代 N 套资源级 suite 各自重复验证
  • ADR-0005 合规：实体仍自序贯，只收编原语，不引擎化

B · 审批窗口谓词端口化 ApprovalDeadline

Strong

Files

  • approval_deadline.ex:62-127 （真源：derive / overdue? / in_window?）
  • 裸 SQL 端口 ×10+：join_request:190 · enrollment:434,609 · sponsorship:574,697,740 …
  • Ash expr 端口：approval_reminder_worker.ex:67-70（in_window? 重编码）
  • inline 绕过：notification_worker.ex:47-78 两处逐字重实现 overdue?，不调真源

Problem

「pending 且窗口未过」这一谓词以 4 种载体出现 ≥12 处。ApprovalDeadline 自称唯一真源，但只有派生面收敛了——谓词面 module 有 interface 无 leverage：NotificationWorker 已经绕过它 inline 重实现。窗口边界语义一旦调整（严格性 / nil 语义），需要找到全部 4 种载体——E-10 对账与过期扫描的口径漂移风险正源于此。

Solution

ApprovalDeadline 增加端口面：Elixir 调用方（NotificationWorker / ReminderWorker）直接用 overdue?/2 消 inline；SQL 守卫片段由候选 A 的 ApprovalClaim 统一产出（列名知识 ← derive/1 既有事实）。@expiry_specs 与 48h 窗口常量维持 D7 拍板原位，不 re-open。

Benefits

  • 与 A 协同：claim SQL 的守卫即谓词端口，一次深化两处收敛
  • 对账 / 过期 / 提醒三方口径结构性对齐（E-10 漂移风险消除）
  • 测试面：谓词语义 1 套属性测试替代 12 处各自验证

F · 赞助两级审批人：读写面不一致

⚠ 潜伏 bug：admin 的待办清单列出 workspace 级 pending 赞助，但 SponsorshipApprover 拒绝 admin 审批——看得到、点不动
Strong

Files

  • policies/sponsorship_approver.ex:26-43 （写面：Event 级=manage / Workspace 级=仅 Owner）
  • workers/approval_reminder_worker.ex:119-125（提醒收件人：同规则第二份陈述）
  • events/pending_approvals.ex:72-88 （读面：managed_workspace_ids 无 level 区分）

Problem

「谁是审批人」这条规则有三份陈述，且读面与写面实际不一致：admin 在待办清单看到 workspace 级赞助 pending（读面按 manage_role? 收窄、无 level 过滤），点审批被 policy 拒绝（写面仅 Owner）。规则有真源（SponsorshipApprover）但 interface 只覆盖 policy 判定，没覆盖「列待办」和「提醒收件人」两个消费面。

Solution

SponsorshipApprover 暴露 approver_roles(level) 唯一读取面：提醒选择器与 PendingApprovals 行级过滤都消费它；待办清单只展示 actor 实际可决策的行。修 bug + 收敛三份陈述一步到位。

Benefits

  • Locality：两级规则一处改动，三个消费面同步
  • 测试面：approver_roles 表驱动测试 + 一个「admin 看不到点不动的行」回归测试

C · save_step_output 鉴权立场 locality

Worth exploring

Files（learner output loop 主路径，plan 020 热点）

  • workflows/workflow_run.ex:454-467（bypass：member OR ActorIsEnrolledLearner）
  • mcp/tools/save_step_output.ex:76-93（工具层 authorize：同规则第二份陈述）
  • mcp/wrapper.ex:16-27 （@membership_deferred 例外清单——声明在工具模块之外）
  • policies/actor_is_enrolled_learner.ex:41-50（谓词委托 StepAuthorization——已单源，好）

Problem

谓词本体单一实现，但组合规则「member OR 学习 run 报名学员本人」在资源 policy 与工具 authorize 各写一遍；更糟的是 Wrapper 的 @membership_deferred 把「本工具豁免成员门槛」的声明放在了工具模块之外——locality 破坏：新写一个非成员可用的工具，必须知道去 wrapper.ex 改清单。

Deletion test（最差形态）：删掉 @membership_deferred 中的条目——无编译错误、无测试直接对应，save_step_output 静默退回 member-only，学员全部 403。删除后复杂度不扩散，但正确性崩。

Solution

鉴权立场声明下沉到工具模块自身（Anubis component 侧 opts，如 membership_gate: :deferred），Wrapper 反射工具声明消费；或彻底单源化到资源 policy，工具层只做 404 形态处理。

D · 通知类型契约 registry 化

Worth exploring

notification_subscriber → fanout → worker → service → miniprogram/client

发一封通知要跨 5 个 module + 一个不成文契约（template_key ↔ data 键集 ↔ job_meta ↔ unique 语义）。stale 重查谓词按资源手写（且重实现 overdue?，见候选 B）。新增一种提醒（join_request 目前就没有）= 改 4 处。

Solution：通知类型声明为数据——registry 条目（template_key + payload builder + stale 谓词 + unique 窗口），NotificationWorker 退化为解释器；stale 谓词接 ApprovalDeadline.overdue?（吃 B 的红利）。

Deletion test：NotificationFanout 本体通过（真深模块，不动）；「通知类型」无载体——Worker 的 stale 子句删除则静默发过期提醒。

E · learning run ↔ enrollment 锚定单源

Worth exploring

step_authorization:114-151 · learning_instantiator:140-146 · learning_progress_worker:183-193

「learning run 锚定到哪条 Enrollment」的概念在 Elixir 里有三份私有拷贝（enrollment_id_of / fetch_enrollment，string/atom 双键处理重复，错误原子各自发明：:error / :enrollment_read_failed / :enrollment_not_found），另有 SQL 与 GraphQL 各一份表达（可接受）。

Solution：Enrollment 侧或 WorkflowRun 侧出 anchor/1 唯一读取面，三拷贝回流。Deletion test：纯赚。处于 plan 020 热点路径上。

G · SignalSubscriber：验证为健康（不建议重构主体）

Speculative

四幂等策略骨架通过 deletion test：删掉则 claim 键派生 / rescue 壳 / telemetry / DOWN 重订阅复杂度扩散到 6 个订阅方——真深模块。测试面已良好（signal_subscriber_test 四策略 + fixtures）。唯一结构性弱点：claim_in_handle 策略（LearningInstantiator）要求模块在 handle 内自行调 claim——骨架无法结构性保证时机，忘调则静默退化为 state_based。小深化方向：handle 接收 claim-once 闭包，或拆 before_claim / effects 两回调，把时机约束从 moduledoc 纪律变成结构。

Top recommendation

先做 A + B（一个 PR 内协同）：ApprovalClaim 收编原子抢占原语，ApprovalDeadline 补齐谓词端口

最大 locality 收益
14 份拷贝 × 7 资源收成 1 个深 module；下一个 intake 资源（invite batch 热点）直接消费而不是再抄。claim SQL 的 deadline 守卫片段就是 B 的谓词端口——一次深化、两处收敛。
测试面收益最大
TOCTOU 并发抢占从 N 套资源级 suite 收成 1 张表驱动契约；谓词语义 1 套属性测试替代 12 处。E-10 对账与过期扫描口径结构性对齐。
零 ADR 摩擦
实体仍自序贯（ADR-0005 合规）、不引擎化；能力外置为 change 原语（ADR-0003 方向一致）。sponsorship.ex 的读回消歧就是现成范本。

F 是潜伏 bug 且体量小，可以随手先行（approver_roles 一处 + 行级过滤）；C 风险形态最差（静默 403）但改动面小，适合在下次动 plan 020 区域时顺手做；D/E 排后；G 只在下次动 signal_subscriber 时考虑。
