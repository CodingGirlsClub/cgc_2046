## 二、关键调研结论(带证据)

### 2.1 Ash 多租户 + MCP 作用域(hexdocs ash/multitenancy 已读 + D12)

- **attribute 策略**:租户资源加 `multitenancy strategy: :attribute, attribute: :workspace_id`;所有查询自动按 tenant 过滤。
- **set_tenant 必须在认证 plugs 之前**(`Ash.PlugHelpers.set_tenant(conn, tenant)`),因为 User/Token 校验需要正确的租户上下文。
- **全局资源**(User / Workspace)不带多租户;租户资源(User 之外的业务资源)带 `workspace_id`。
- Code interface / action 内可用 `Ash.Query.set_tenant/2`、`Ash.Changeset.set_tenant/2`;`Ash.Scope` 可打包 actor/tenant/context。
- **两个 Api 模块**:`Cgc2046.Api`(租户资源,默认要求 tenant)+ `Cgc2046.GlobalApi`(User/Workspace)。
- **MCP 作用域(D12)**:OpenClacky 的 MCP client 是 **server 级全局长连接**(进程级共享)→ 不能存服务端会话状态(会跨会话串)。因此所有 MCP 工具带**必填 `workspace_id`**(无状态、每调用鉴权 + 审计);"当前工作区"由用户侧 CGC 助手维护。

### 2.2 anubis_mcp(网站 MCP server,替代 ash_ai)

- **定位**:网站暴露**一个** MCP server(Elixir/Phoenix,活跃维护);用户的 OpenClacky 以 `type: http` 连接(`url: https://cgc.example.com/mcp`,D13)。
- **协议**:MCP(JSON-RPC 2.0 over HTTP + SSE);工具经 `tools/list` / `tools/call` 暴露;工具内部调用 Ash actions,复用同一授权链(D6)。
- **认证**:每用户连接 token 放 `Authorization: Bearer <token>` 头;token 绑**用户不绑工作区**(D13),租户由每次调用的 `workspace_id` 参数判定(D12)。
- **与 GraphQL 的关系**:GraphQL 供网站 UI;MCP 供用户 OpenClacky。两者共享同一批 Ash resources/actions 与 RBAC,不重复实现业务逻辑。
- **Mock 方式**:工具测试直接调用工具模块(或经 anubis_mcp 的测试钩子),无需真实 OpenClacky。

### 2.3 ash_authentication 4.14.1(认证 + 连接 token)

- 策略:Password / ApiKey / Auth0 / Github / Google / MagicLink / Slack / OAuth2 / Oidc → **本平台用 Password(用户名+密码)+ 邀请链接**(MagicLink 作为备用体验)。
- Token:`AshAuthentication.TokenResource`(短期 JWT,`sign_in` mutation 返回);`Confirmation`(邮箱确认,邀请场景)。
- **MCP 连接 token(D6/D13)**:每用户一个连接 token(网站"连接设置"生成,绑用户、可多 Workspace、按目标资源判定租户);平台只存 hash,撤销立即失效;邀请 token 存 hash(不存明文)。
- 前端集成:GraphQL `signIn(email:, password:)` → token → cookie → `Authorization: Bearer` 头;后端 `AshAuthentication.Plug` 验证。

### 2.4 AgentRun 与工具审计(重定义,D9)

- **网站自动记录每次 MCP 工具调用**(审计流:谁 / 工具 / 参数 / 结果 / 确认 / 时间)→ `ToolCallLog`。
- **AgentRun = 按 Step 聚合的"一次干活"记录**:操作序列摘要、关联 Step、操作者;由网站根据工具调用自动生成,**v1 就做**。
- **不做用户侧上报**(上报不可靠/可篡改、连接器扩展工作量大)。
- 用户侧 OpenClacky 对话 / token 用量等执行详情**不进 AgentRun**。

### 2.5 前端(Next.js 16 + Apollo 4,形态 X)

- 脚手架现状:`app/apollo-provider.tsx`("use client" + ApolloProvider)、`lib/apollo-client.ts`(`createHttpLink` + `InMemoryCache`)、layout 已包裹。
- 补充:middleware/rewrite 代理;Apollo link 中间件加 Authorization。
- **页面形态(D4)**:无对话页 / 无执行页;新增连接引导页(三步 onboarding,D13)与审计查看页(v1)。

### 2.6 连接器扩展 cgc-2046(用户侧统一入口,D14)

- **命名(D14)**:扩展 id `cgc-2046`;MCP server 条目名沿用 `cgc-2046`;本地技能前缀 `cgc2046-<ws>-<skill>`(防多工作区撞名,D12)。
- **单一配置点 = mcp.json(D13)**:扩展自动读 mcp.json 的 cgc-2046 条目拿 URL + token,**零额外配置**;扩展**不代写** mcp.json(避免被覆盖)。
- **静态内置通用"CGC 助手" agent(D10)**:用户说"用教研 Agent"→ 助手经 MCP `get_agent_instruction(workspace_id, agent_id)` 拉取网站上的 Agent 定义(prompt/skills/授权)→ 按定义工作。公共 Agent 动态创建天然支持;不做运行时下发文件。
- **工作区 Skill 同步(D11)**:工作区 Skill 定义存网站;扩展经 API handler(经 `@http_server` 访问 `@skill_loader`,与 session_manager 同模式)调 `SkillLoader#create_skill / delete_skill` 运行时写 `~/.clacky/skills/` + 立即注册(已源码验证)。**角色过滤在网站侧**(扩展只拉到该用户角色可见的技能);触发方式:扩展静态打包 `cgc-sync` skill / aside 面板按钮。

### 2.7 确认流(D8):原生 request_user_feedback

- Agent 调高风险 MCP 工具(审批/授权/邀请/策略/删除类)→ 网站**不落业务库**,建 PendingOperation → 返回 `needs_confirmation: {id, 摘要}`。
- Agent 调内置 `request_user_feedback(question, options: ["确认写入", "继续讨论"])` → 用户 OpenClacky WebUI 弹可点击卡片,Agent 停下。
- 用户点选 → 文本回传 Agent → Agent 调 `confirm(id)` → 网站**落业务库 + 审计**。
- **无 confirm 不落库**;已知风险:auto_approve 10s 倒计时自动决策(二期加冷却期)。

## 三、自研 RBAC 设计(核心,需写清楚)

### 3.1 数据模型

```
User(全局) ─── WorkspaceMembership(1 条/人/租户) ──── MembershipRole(N:M) ──── Role(租户内)
                                                     MembershipRole.role_id ──→ Role.id
Workspace(全局, join_policy)  Role 挂 allowed_roles(Agent 资源引用 Role.id 集合)
```

### 3.2 判定逻辑

- **多角色**:一个成员多条 MembershipRole → 权限 = 所有角色权限**并集**,命中任一即放行。
- **Step 授权**:`StepRole` 关联表(step_id, role_id);执行动作时要求成员的角色集与 Step 允许角色集**有交集**。
- **Agent 授权**:Agent 资源 `allowed_roles: [Role.id]`(公共 Agent 独立授权)。
- **MCP 调用同一授权链(D6)**:每次 MCP 工具调用 = token 认证 → 定位身份(成员关系)→ RBAC 判定 → 资源/Step 级(workspace_id 过滤)→ 执行 + 审计;**Agent 权限 = 用户本人权限,越权被拒**。

### 3.3 Ash 实现方式(不用 AshRbac)

- 每个租户资源 `policies` 里用**自定义 authorize** 或 `expression` 引用 Rbac 模块,示例:

```elixir
policies do
  policy action_type(:read) do
    authorize_if expr(workspace_id == ^actor_workspace_id)  # 租户内可见
  end

  policy action_type([:update, :destroy]) do
    authorize_if Cgc2046.Rbac.can?(actor, :manage, resource: __MODULE__)
  end
end
```

- `Cgc2046.Rbac.can?(actor, permission, opts)`:读 actor 的 memberships(membership + roles 预加载),并集展开权限集,返回布尔。
- 统一约定:**所有写操作(action)首行 `Rbac.ensure!(actor, :xxx)`**,失败返回 Forbidden;MCP 工具同样先 `Rbac.ensure!` 再执行。

## 五、测试策略细节

- **后端**:ExUnit;Ash 资源的 `api.create!/read!`;租户隔离测试用两个 tenant 各造数据断言互不可见;**MCP 工具测试直接调工具模块/anubis_mcp 测试钩子**(网站不跑 LLM,无 LLM mock)。

- **前端**:Vitest + @testing-library/react(组件 + hooks);页面 = 工作台/产出展示/审计/连接引导(无对话页)。

## 六、风险与注意点

1. **AshRbac 不适用**(角色编译期)→ 自研 Rbac,注意"多角色并集"与"Step/Agent 交集"两种判定不要混。
2. **set_tenant 顺序**:放在认证 plugs **之前**,否则 User 校验拿不到租户上下文(全局资源除外)。
3. **anubis_mcp 较新**:锁定版本,关注 MCP 规范演进(tools/list、tools/call、HTTP/SSE transport);升级前看 changelog。
4. **OpenClacky MCP client 为 server 级全局长连接**(D12):不能存服务端会话状态 → 所有 MCP 工具必带 `workspace_id`,每调用鉴权 + 审计。
5. **多租户 + 全局混合**:User/Workspace 全局,其余全部租户;创建租户资源的 action 必须显式 set_tenant(从 actor 的 membership 取 workspace_id),防止跨租户写入。
6. **token 安全**:网站登录 token 存 httpOnly cookie;MCP 连接 token 绑用户不绑工作区、平台只存 hash、撤销立即失效;邀请 token 存 hash。
7. **平台零 AI 成本(BYO,D3)**:不再有网站侧 LLM 成本;用户离线则该用户 Agent 任务不可用(接受)。
8. **确认流安全(D8)**:无 confirm 不落业务库;PendingOperation 过期清理;auto_approve 10s 自动决策二期加冷却期。
9. **扩展不代写 mcp.json(D13)**:单一配置点 = mcp.json,扩展只读不写,避免被覆盖。
