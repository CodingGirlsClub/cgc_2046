# 小程序订阅消息：构建注入契约与真机验证清单

> 关联：issue #635（7 个订阅模板的前端订阅触点）、#606（投递管线）、PR #639（渲染子句 + 17 键 allowlist）
>
> 本文档定义小程序侧订阅消息模板 ID 的**注入契约**、**人工构建 runbook** 与**真机验证清单**。它是发布小程序时的唯一事实来源。

## 1. 为什么需要这份文档

后端侧（`WECHAT_MP_TEMPLATE_*` → `runtime.exs` → `Consent.template_configured?`）已由
`backend/test/cgc_2046/notifications/template_allowlist_test.exs` 守卫，PR #639 把四处名单钉成同一集合（#546 后为 **18 键**）。

**但小程序产物是另一条注入链，且没有任何 CI 覆盖**：`.github/workflows/deploy.yml` 的 job 只有
`changes / backend / web / smoke / notify`——**没有 miniprogram job**。小程序的生产产物由人工在本机构建并上传。

后果：即使后端 17 个模板 ID 全配好、前端触点全部就位，**只要构建机没导出模板 ID，用户点了授权也拿不到模板 ID，一条消息都送不出去**。这正是 #606→#635 那条「以为接通了其实没送到」链条的最后一环。

## 2. 注入契约

### 2.1 变量清单（13 个）

| 变量 | 场景键 | 收件人 |
|---|---|---|
| `CGC_WECHAT_TEMPLATE_APPROVAL_RESULT` | `approval_result` | 报名者（审批结果） |
| `CGC_WECHAT_TEMPLATE_APPROVAL_REMINDER` | `approval_reminder` | Owner/Admin（待审批提醒） |
| `CGC_WECHAT_TEMPLATE_EVENT_REMINDER` | `event_reminder` | 报名者（活动开始） |
| `CGC_WECHAT_TEMPLATE_EVENT_QUALIFICATION_CONFIRMED` | `event_qualification_confirmed` | 报名者（成班/开班确认） |
| `CGC_WECHAT_TEMPLATE_EVENT_QUALIFICATION_UNDERFILLED` | `event_qualification_underfilled` | 报名者（未达阈值） |
| `CGC_WECHAT_TEMPLATE_EVENT_SCHEDULE_CHANGED` | `event_schedule_changed` | 报名者（改期） |
| `CGC_WECHAT_TEMPLATE_EVENT_MODERATOR_ASSIGNED` | `event_moderator_assigned` | 被指派的主理人 |
| `CGC_WECHAT_TEMPLATE_SPEAKER_ACCEPTED` | `speaker_accepted` | **Owner/Admin**（分享者已接受） |
| `CGC_WECHAT_TEMPLATE_SPEAKER_COMPLETED` | `speaker_completed` | Owner/Admin + 分享者本人 |
| `CGC_WECHAT_TEMPLATE_LEARNING_STAGNATION` | `learning_stagnation` | 学习者（学习停滞） |
| `CGC_WECHAT_TEMPLATE_ENROLLMENT_CHECK_IN_CODE` | `enrollment_check_in_code` | 报名者（报名落 confirmed 时下发 6 位核销码，#546） |
| `CGC_DOUYIN_TEMPLATE_APPROVAL_RESULT` | `approval_result` | 抖音裁剪端（模板未申请，空） |
| `CGC_DOUYIN_TEMPLATE_EVENT_REMINDER` | `event_reminder` | 抖音裁剪端（模板未申请，空） |

键名规则：`CGC_WECHAT_TEMPLATE_` + 场景键的 `SCREAMING_SNAKE`，**机械可推**——由
`miniprogram/config/index.ts` 的 `WECHAT_SCENARIOS` 列表驱动，不逐条手写。

### 2.2 消费链

```
.env.prod（构建机本地，gitignore）
  └─ config/env.ts          dotenv 装载 → process.env
       └─ config/index.ts   WECHAT_SCENARIOS 列表 × env → __WECHAT_TEMPLATE_IDS__（单一 JSON blob）
            └─ Taro defineConstants 内联为对象字面量
                 └─ src/platform/index.ts  读 blob → configuredScenarios() 过滤空值
                      └─ Taro.requestSubscribeMessage({ tmplIds })  ← 单次上限 3
                           └─ src/api/real.ts  grantConsent(scenario) → 后端 +1 配额
```

### 2.3 三条硬约束

1. **模板 ID 不得提交进仓**（#635 红线）。`.env.prod.example` 只留空占位；
   2026-08-26 曾把 3 个真实 ID 提交进仓，造成「example 与 secrets 两份真源」。
   守卫测试 `miniprogram/tests/subscription-build.test.mjs` 拒绝任何
   `*TEMPLATE*` 键的非空值，以及源码里形如模板 ID 的引号字面量。
   ⚠ **gitleaks 拦不住这种形态**（默认规则不认 43 位 base64url），所以必须靠该测试。
2. **缺配 fail-closed**：未配置的场景在请求期被 `configuredScenarios()` 剔除，
   绝不把空串递给微信（空串会让整次调用失败或错配模板）。剔除后为空则抛可读错误。
3. **单次上限 3**：`requestSubscribeMessage` 的 `tmplIds` 一次最多 3 个，且必须由
   用户点击或支付回调触发。触点的场景组合由 `src/domain/subscription.ts` 定义并由
   `tests/subscription-domain.test.ts` 断言不越界。

## 3. 人工构建 runbook

```bash
cd miniprogram

# 1) 准备 env（.env.prod 已在 .gitignore:11，不会被提交）
cp .env.prod.example .env.prod
# 填入 CGC_GRAPHQL_ENDPOINT + 11 个微信模板 ID（值来自微信公众平台
# 「功能 → 订阅消息 → 我的模板」，与后端 GitHub secrets 同源）

# 2) 确认 11 个值都非空（缺一个就会少一条通知路径）
grep -c '^CGC_WECHAT_TEMPLATE_[A-Z_]*=.\+' .env.prod   # 期望 11

# 3) 构建（weapp 为生产目标）
./node_modules/.bin/taro build --type weapp

# 4) 验证注入落进产物（应看到 11 个键、值非空；缺配时值为 ""）
grep -rho '{approval_result:"[^}]*}' dist/weapp/ | head -1

# 5) 微信开发者工具「上传」→ 公众平台提审 → 发布
```

**构建后自检**：第 4 步若看到 `approval_result:""`，说明 env 未生效——检查
`.env.prod` 是否在 `miniprogram/` 目录下、变量名是否拼错。

## 4. 真机验证清单

> 真机验证**不阻塞**代码合并；第 1 次真实发送后才能确认。

| # | 验证项 | 期望 | 失败回退 |
|---|---|---|---|
| 1 | **授权链路**：报名结果页点订阅 → 出现 3 个开关的对话框 → 全选接受 | `notification_consents` 出现 3 行、`remaining_uses = 1` | 检查产物内模板 ID 是否非空（§3 第 4 步） |
| 1b | **核销码授权链路（#546，M0）**：活动报名表单点「确认报名」→ **先**弹 1 个开关的对话框 → 接受 → 报名才提交 | `notification_consents` 出现 `enrollment_check_in_code` 行、`remaining_uses = 1`；随后报名落 confirmed 时该通知送达（点开落「我的报名」，页上 6 位码 + 二维码） | ① 产物内第 11 个模板 ID 是否非空（§3 第 4 步）；② 顺序由 `submitAfterCheckInCodeConsent`（`src/domain/subscription.ts`）钉住，页面不得把授权挪到提交之后 |
| 2 | **`date2` 官方形态**（`event_schedule_changed`）：值形如 `2026年9月20日 15:00` | 平台接受、用户收到 | **已写明的两行回退**（`backend/lib/cgc_2046/notifications/service.ex` 的 `date/1` 注释）：① 格式串去掉 `" %H:%M"`（date-only，官方另一种合法形态）；② 该子句 `thing5` 改放「改期至 9月20日 15:00」（15–16 字 ≤20）。**其余子句/名单/测试不动** |
| 3 | **`time3` / `time11` 短横线形态**（`time/1`）：值形如 `2026-09-20 15:00` | 平台接受 | 改 `time/1` 格式串为「年月日」形态（同类两行改动） |
| 4 | **未授权可区分**：把某场景配额耗到 0，再触发一次发送 | 日志出现 `notification not delivered: consent exhausted (template_key=… user_id=…)`；Oban 作业为 `discarded` 而**非** `completed` | 检查后端 `NotificationWorker.perform/1` 的 `:consent_exhausted` 子句 |
| 5 | **outbox 三模板**（`event_qualification_*` / `event_schedule_changed`）未授权时触发 | `notification_deliveries` 行留 `pending` → 末拍 `failed` + `last_error`，规15 出 Finding | — |
| 6 | **生产构建注入**（§3 第 4 步） | 产物内 11 个值非空 | 重跑 runbook |

### 4.1 `date2` / `time` 的已知假设

`date2` 用「年月日 + 24 小时制时刻」，与微信官方示例（`2019年10月1日 15:01`）同形，但
**未经真机验证**（申请方按红线未做测试发送）。暴露点 = 前端触点落地后的首次真实发送。

## 5. 覆盖缺口（有意保留，勿默默补齐）

| 场景 | 缺口 | 现状 |
|---|---|---|
| `speaker_completed` | **分享者本人无入口** | 小程序没有任何分享者面（无分享者 GraphQL 查询、无页面）。后端自己记录「speaker 侧点开无权威页」（`client.ex` 的 `@manager_templates` 注释）。分享者腿的发送会命中 `consent_exhausted`，由 §4 第 4 项的可观测性暴露 |
| `speaker_accepted` | 无 | 收件人是 **Owner/Admin**（不是分享者），入口在工作台 |
| `event_moderator_assigned` | 首次指派送不到 | 鸡生蛋：用户正是通过该通知才首次得知被指派。入口在「已是某活动主理人」的活动详情页，覆盖的是后续指派 |
| `enrollment_check_in_code` | **授权必须在报名提交之前** | 一次性订阅 = 一次授权一条消息，而 open 免费场的 confirmed 与提交同事务落定（通知在提交后数百毫秒发出）→ 结果页/我的报名/支付成功页上的**后置触点必然送不到**。故触点前移到 M0（报名表单提交前）；拒绝授权者仍可在「我的报名」查看核销码 |
| `learning_stagnation` | 近似落点 | 学习行为在 OpenClacky 桌面端（见 `pages/openclacky`），小程序内唯一近似落点是「我的报名」的**课程**卡 |

## 6. 常见故障

| 症状 | 原因 | 处置 |
|---|---|---|
| 点订阅按钮提示「缺少微信订阅消息模板 ID」 | 构建机没导出模板 ID（`configuredScenarios` 剔除后为空） | 按 §3 runbook 重建 |
| 点订阅按钮提示「Consent grant failed」 | 后端 `WECHAT_MP_TEMPLATE_*` 未注入容器 → `template_configured?` 为假 | 检查 `.github/workflows/deploy.yml` 的 secrets 循环与 `backend/config/deploy.yml` 的 `env.secret`（PR #639 / #546 已补齐 18 键） |
| 用户说「授权了但没收到」 | 一次性订阅 = 一次授权一条消息，配额可能已被上一条消耗 | 查 `notification_consents.remaining_uses`；日志里搜 `consent exhausted` |
| 授权后立刻收到「你暂未授权」 | 微信返回 `reject`（用户在对话框里关掉了开关） | 预期行为；按钮保留，用户可再点 |
| CI 在 `subscription-build.test.mjs` 变红 | 场景键集在某处漂移（config 列表 / models 联合 / domain 列表 / env 模板） | 按报错里列出的「仅 X 有」补齐四处 |
