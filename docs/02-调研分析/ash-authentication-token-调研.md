# ash_authentication Token 策略 vs CGC 严格授权链(调研)

> 调研日期:2026-07-31 · 版本:ash_authentication **4.14.1** · 来源:hexdocs 官方模块文档 + GitHub 源码(v4.14.1 tag)+ 官方 tokens guide
> 回答的问题:**ash_authentication 的 token 机制能否支撑我们 OpenClacky 文档 §3 的"严格授权链"**(token 只是身份凭证、每次请求实时算 RBAC、可撤销、按 workspace 签发)?

---

## 一、结论(先说)

**能,而且是这套方案的天然底座。** ash_authentication 提供:JWT 签发(可配置有效期)、Bearer 头每请求加载用户(plug)、**白名单式 token 校验**(`require_token_presence_for_authentication?`)、**按 jti 定向撤销**、**按 subject 批量撤销**(LogOutEverywhere)、可审计(purpose 字段)。RBAC 判定(RBAC 矩阵、Step 授权)不在它的职责范围——正好由我们自研(见 §4),二者互补。

**需要我们自己实现的**(库明确声明):token 生成/撤销/过期/scope 的"业务语义"——即**按 workspace 签发的 token 实体**(绑定 user_id + workspace_id + 能力域 + 有效期 + 可撤销)。ash_authentication 给的是"认证通道",不替我们管"令牌的生命周期策略"。

## 二、证据

### 2.1 JWT 配置(官方 DSL,源码 `lib/ash_authentication/dsl.ex` v4.14.1)

`authentication.tokens` 段支持:

| 配置项 | 默认 | 含义(源码 doc 原文) |
|---|---|---|
| `enabled?` | `false` | "Should JWTs be generated by this resource?" |
| `token_lifetime` | `{14, :days}` | "How long a token should be valid."(`@default_token_lifetime_days 14`) |
| `signing_algorithm` | 列表首项 | "The algorithm to use for token signing." |
| `signing_secret` | 必填 | "The secret used to sign tokens." |
| `token_resource` | 必填 | "The resource used to store token information, such as in-flight confirmations, revocations, and if `store_all_tokens?` is enabled, authentication tokens themselves." |
| `store_all_tokens?` | `false` | "Store all tokens in the `token_resource`." |
| `require_token_presence_for_authentication?` | `false` | "Require a locally-stored token for authentication." |
| `session_unique_id` | `:error` | "Should always be `:jti`, if set"——确认 token 含 **jti**(JWT ID) |

要点:**默认 token 有效期 14 天**,可配置成 `{30, :days}` 等;签名密钥来自配置(生产用环境变量/secret provider)。

### 2.2 撤销机制(官方模块族)

- `AshAuthentication.TokenResource.IsRevoked` + `IsRevokedPreparation`——校验时检查 token 是否已撤销(默认黑名单语义)。
- `AshAuthentication.TokenResource.RevokeJtiChange`——**按 jti 撤销单个 token**(我们的"一键撤销某个 API token"直接对应)。
- `AshAuthentication.TokenResource.RevokeAllStoredForSubjectChange`——按 subject(用户)撤销全部。
- `AshAuthentication.TokenResource.Expunger`——周期清理过期撤销记录(配合 `AshAuthentication.Supervisor` 启动)。
- `AshAuthentication.AddOn.LogOutEverywhere`——add-on,`log_out_everywhere` action 撤销用户全部未过期 token;可 `exclude_purposes` / `include_purposes` **按 purpose 定向**。
- 官方 tokens guide(tokens.md)原文:
  > "`require_token_presence_for_authentication?` inverts the token validation behaviour from requiring that tokens are not revoked to requiring any token presented by a client to be present in the token resource to be considered valid. Requires `store_all_tokens?` to be `true`."

  **这就是"白名单模式"**:token 必须在 token_resource 里存在才算有效——比黑名单(未撤销即有效)更强,正好匹配"平台签发的 CGC API token 才有效"的需求。
- 官方 guide 同时声明:**"Since refresh tokens are not yet included in `ash_authentication`"**——没有内置 refresh token;长生命周期 token 或自实现刷新。

### 2.3 每请求认证(plug)

- `AshAuthentication.Plug`:`load_from_bearer`(API 场景)+ `load_from_session`(浏览器场景)。示例(`AshAuthentication.Plug` 模块文档):
  ```elixir
  pipeline :bearer_users do
    plug :load_from_bearer
  end
  ```
  即**每个请求**从 `Authorization: Bearer <token>` 解析并验证 token、加载用户。用户信息进 `conn.assigns`,供后续 controller/GraphQL 管道使用。
- token 到用户:`AshAuthentication.user_to_subject/1` → `"user?id=<uuid>"`;`subject_to_user/2` 反查(见主模块文档)。

### 2.4 API Key 策略(机器对机器凭证)

- `AshAuthentication.Strategy.ApiKey`——为 API key 认证设计。文档明确:
  > "Responsibility for generating, securing, expiring and revoking lies on the implementor."
  
  (生成/加密/过期/撤销的责任在实现者——与 §一 结论一致。)
- 类型字段含 `api_key_hash_attribute`(哈希存储)、`multitenancy_relationship`(**多租户关系**——与我们按 workspace 签发 token 的诉求对齐)、`sign_in_action_name`。
- 登录后可检测:`user.__metadata__[:using_api_key?]`、`user.__metadata__[:api_key]`,可用于写基于 key 的 policy。

## 三、与 CGC 严格授权链(OpenClacky 文档 §3)的映射

| CGC 严格授权链环节 | 由谁承担 | 备注 |
|---|---|---|
| 1. 认证(token 有效、未撤销/在白名单) | ash_authentication(`load_from_bearer` + token_resource) | `store_all_tokens? true` + `require_token_presence_for_authentication? true` 启用白名单模式 |
| 2. 定位身份(用户 + workspace 成员关系) | 平台业务层(自研):token 实体绑定 user_id+workspace_id → 实时查成员/角色 | ash_authentication 只给 user;workspace 上下文由我们的 token 实体携带 |
| 3. RBAC 判定(角色 × 操作 × 资源) | **自研 Rbac 模块 + Ash.Policy.Authorizer**(见 §4) | 每次请求实时算,不缓存(文档 §3.1 原则) |
| 4. 资源/Step 级授权 | Ash policies(owner 校验、Step.allowed_roles、set_tenant) | 多租户隔离由 Ash 多租户 + token 绑定的 workspace 共同保证 |
| 5. 审计 | `AshAuthentication.AddOn.AuditLog`(登录侧)+ 自研 audit_log(业务操作侧) | 登录失败也可记(AuditLog 文档:`return_error_on_invalid_magic_link_token?`) |

## 四、落地建议(写进实施计划)

1. **CGC API Token 实体**(自建 Ash resource `ApiToken`):字段 `user_id`、`workspace_id`、`name`、`token_hash`(只存哈希,不落明文)、`scopes`(read / workflow:write / agent:write)、`expires_at`、`revoked_at`。签发/撤销是普通 Ash action,受 RBAC(谁能签发、谁能撤销)。
2. **认证通道**:Phoenix 管道 `plug :load_from_bearer`(ash_authentication)+ 自定义 plug 读 `ApiToken` 表验证白名单/有效期 → 得到 `%{user, workspace, scopes}` 上下文。
3. **授权层**:全部写在 **Ash 资源 policies**(`policies do ... end` + 自定义 `Ash.Policy.Check`),REST controller 与 GraphQL mutation 都是薄壳走同一 Ash action——**两层入口共享同一安全判定**(这同时是 REST vs GraphQL 决策的关键依据,见另一份调研)。
4. **撤销**:`ApiToken.revoked_at` 置位即全局失效(每次请求查表,不做缓存信任);"撤销所有"(换绑/失窃)→ 遍历该 user 的 ApiToken 批量置位,或 LogOutEverywhere 按 subject 撤销 JWT。
5. **有效期**:默认 `{30, :days}`(库默认 14 天,可覆盖);无内置 refresh token → 到期重新签发(网站设置页一键生成),不做自动刷新,保持简单。
6. **scope 校验**:在自研 plug 或 policy 中检查 `scopes` 是否含所需能力域——最小权限签发,防止"一个 token 能干所有事"。

## 五、风险与注意点

- **token 泄露面**:token 存用户本地(OpenClacky config);平台只存 hash——与 OpenClacky 文档 §3.4 一致。
- **性能**:白名单模式每个请求查 token_resource 表(索引 `token` 哈希字段);高并发可加缓存,但**撤销即时性优先**,先不缓存。
- **`session_unique_id`**:必须设 `:jti`,否则多 token 语义(按 workspace 多个 token)会乱。
- **无 refresh token**:长生命周期(30 天)+ 可撤销可覆盖需求;若未来要短 token+刷新,自实现(官方 guide 明示)。
