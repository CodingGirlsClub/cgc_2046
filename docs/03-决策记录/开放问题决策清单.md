### 1.2 背景与证据

- 现象：同一 workflow 内用 join 等待两个以上异步信号，在 Agent 策略（auto）下死锁——feed1 后 join 进入 ran_nodes（视为"已执行"）；feed2 时 join 已满足却被 ran_nodes 过滤，create/notify 永不执行（POC §3.3 双向证明）。
- 定性：这是 **jido_runic 1.0 Agent 策略层的引擎缺陷**，非设计错误，也**非 runic 引擎缺陷**（原生 runner 无 ran_nodes 概念，`Workflow.react/2` 直接驱动靠图边状态，join 每次 fact 到达都会重新 prepare → 无死锁）。v1 主路径**固定 Workflow 层（runic 直接驱动）本身就是 jido 原生能力，非"绕行"**；**审批两段式**是 Agent 策略场景下规避缺陷的**架构层手段**（业务异步审批需要 + 缺陷未修复前规避；第一段落 DB + 第二段信号恢复），配合"主路径固定 Workflow 层"成为**既定架构决策**。
- 根治路径：根因与修复已定位（**2026-08-01 调研**）——修复点单文件单函数（`jido_runic/lib/jido/runic/strategy.ex` `handle_apply_result` 无条件 `MapSet.put(ran_nodes, runnable.node.hash)`，即使 join 仅 `result=:waiting` 占位），一行级改动（`result==:waiting` 时不记 ran_nodes），修复方案 POC 已验证（patch 后重跑 `verify_9_f1_repro.exs` PASS，恢复原码 FAIL，双向证明）。属二期（Agent 策略场景出现时）——**双管齐下**：① 上游提交 ran_nodes 修复 PR（一行级，低依赖）；② Agent 层标准写法采用官方 **Coordinator fan-in**（signal_routes + 状态聚合，orchestration guide 先例，POC 已验证）。
- 涉及文档：poc-验证报告.md §3.3；报名workflow详细设计.md §6；赞助workflow详细设计.md §6；教研workflow详细设计.md §6（F12 同源）；Jido_Workflow架构研究员/f1-jido-native-solutions.md（2026-08-01 源码根因定位 + C1–C5 方案对比 + C3 修复 POC 验证）。

## 二、F7 🟡 审批超时语义 —— ✅ 已拍板（方案 A，用户 2026-08-01）

**现状**：审批（报名 pending / 赞助 pending）超时策略未定死：设计默认"无超时自动拒绝（人为决策）"，"可选 N 天自动过期"标注为可选。影响 hibernate 挂起时长与运维 SLA。

**架构可视化工程师建议**：7 天自动过期 + 过期前提醒，WorkflowDefinition 暴露 `approval_timeout` 参数；或保持无超时但需保证长期 waiting 不耗资源。

**用户拍板（2026-08-01）：采用方案 A**——`approval_timeout` 默认 7 天自动过期 + 过期前 48h 提醒 + `expired` 独立终态可重提。本清单 §2.1 方案 A 为既定决策，同步修订报名/赞助 workflow、领域模型定稿、引擎 DDD 设计、用户旅程与 Web 功能清单（见 §2.3 影响面）。

### 2.1 既定方案 A（用户拍板，2026-08-01）

- **默认值**：`approval_timeout = 7 天`（报名 pending / 赞助 pending 统一默认；参数可按 workflow 配置，`null` = 无超时）。
- **过期语义**：run 转 **`expired`**（业务终态，区别于 `rejected` 拒绝——语义为"未及时审批自动失效"，非否定申请）。
- **提醒**：deadline 前 **48h** 向审批人发一次提醒（站内通知/后台审批页置顶），避免无感知过期。
- **可重提**：过期后申请者/赞助方可**重新提交**（新 run，`request_id` 区分，幂等键不冲突）；审批页保留"已过期"历史记录。

**理由**（业务 SLA + 引擎成本双视角）：
1. **业务 SLA 可承诺**：报名/赞助申请者知道最晚 7 天有明确结果（过期也是明确结果），避免无限等待；社区活动周期一般 2–4 周，7 天审批窗口与活动节奏匹配（Sponsor 为 B 端意向，若运营需要可配置 14 天，参数已支持）。
2. **自动过期 ≠ 拒绝**：语义上保留"可重提"，避免审批人只是没来得及、申请被误判为否定；`expired` 独立终态使状态机语义干净（pending → approved | rejected | expired）。
3. **引擎成本最低**：过期路径 = deadline 到点唤醒（hibernate + Schedule Directive），与 F2（报名截止 cancel 唤醒）**同一机制**——F2 集成测试一旦补齐，F7 过期路径直接复用验证，一次投入两处受益。
4. **运维干净**：pending 队列不会无限积压，审批页列表可控；无超时则需额外巡检与人工清理，SLA 无法承诺。

**实现要点**（若用户采纳）：
- WorkflowDefinition 新增 `approval_timeout`（默认 7 天，`null` = 无超时；审批节点级可覆盖）。
- 进入 waiting 时登记 deadline；由调度（Schedule Directive / 定时检查）在 deadline 到点唤醒 → run 转 `expired`；deadline-48h 触发提醒信号。
- 状态机：报名/赞助 pending 增加 `expired` 分支（见 F4 预声明：状态机改动走快照机制，不影响已运行 run）。
- 依赖 F2 集成测试（deadline 到点唤醒 → cancel/expired 断言）。

### 2.2 备选方案 B（不推荐默认）：保持无超时

- **做法**：无自动过期，审批完全靠人；长期 waiting 依赖 hibernate 挂起（POC-2 G1 已验证不耗常驻资源）。
- **成本**：依赖 F2 验证（长期 waiting 资源占用）+ 运维巡检清理积压 pending；审批人遗忘则申请者无限等待，SLA 不可承诺。
- **适合**：审批人承诺 24h 内处理的小团队、待审量极低的场景；不适合作为平台默认。
