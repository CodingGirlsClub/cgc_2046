## 背景一句话

原技术方案（网站用 ash_ai 自行实现 AI Agent）被推翻：**网站不再自己跑 LLM/Agent，改为网站做业务中枢 + MCP server，用户自带 OpenClacky 做 Agent 执行**（BYO，自带模型）。

---

## 决策清单

### D1. 删除 ash_ai
网站不再自行实现 AI Agent（不跑 LLM/ToolLoop）。网站做 client 侧业务中枢，OpenClacky 做 Agent 执行（经 MCP/CLI 对接）。

### D2. 领域模型：Agent / AgentRun 重定义
- **Agent 保留** = 授权/配置登记：`type / allowed_roles / owner` + OpenClacky 配置引用（`openclacky_profile / model / system_prompt / skills`）。
- **AgentRun 保留** = 领域操作聚合记录：网站根据 MCP 工具调用自动生成（见 D9），v1 就做。

### D3. BYO 粒度 = 每用户强制安装 OpenClacky
- 平台提供安装命令；onboarding = 安装引导。
- 平台零 AI 成本；连接方向 = 用户侧主动连（出站、无隧道）。
- 用户离线则该用户 Agent 任务不可用（接受）。

### D4. 网站 UI = 形态 X（无对话/执行页）
网站专注业务中枢：工作台、成员/角色、Workflow 产出展示、审批、审计查看。聊天全在用户自己的 OpenClacky。

### D5. 通道：B 通道（网站 MCP server）为主干，A 通道（网站派活）消失
网站派活不再存在；网站通过暴露 MCP server 被用户的 OpenClacky 调用。

### D6. 连接模型：单 MCP server + 每用户 token + RBAC
- 网站暴露**一个** MCP server（技术选型：anubis_mcp，Elixir/Phoenix，活跃维护）。
- **每用户一个连接 token**：绑用户、可多 Workspace、按目标资源判定租户。
- MCP 调用 = 用户本人身份 + 网站 RBAC 强制（Agent 权限 = 用户权限，越权被拒）。
- 原则：**工具 = 形状、租户 = 过滤器、每次工具调用 = 审计记录**。

### D7. MCP 工具集：读 + 写 + 管理类全进
- 读：`get_workspace_context / get_workflow / get_step_output / list_members / get_learner_history`
- 写：`save_step_output / reply_learner_question`
- **管理类也进 MCP**（用户拍板）：Agent = 用户的执行分身，RBAC 兜底。
  - 低风险直做：`create_agent / create_workflow` 等
  - 高风险确认流：`approve_join_request / assign_role / create_invitation / update_join_policy / 删除类`

### D8. 确认流 = 方案二（原生 request_user_feedback）
1. Agent 调高风险 MCP 工具 → 网站**不落库**，建 pending 记录 → 返回 `needs_confirmation: {id, 摘要}`
2. Agent 调内置 `request_user_feedback(question, options: ["确认写入", "继续讨论"])` → WebUI 弹可点击卡片，Agent 停下
3. 用户点选 → 文本回传 Agent → Agent 调 `confirm(id)` → 网站落库 + 审计
4. 网站永远不偷偷执行（**无 confirm 不落库**）
- 已知风险：auto_approve 模式 10s 倒计时自动决策（二期可加冷却期）。

### D9. AgentRun = 领域操作聚合（选项 1）
- 网站自动记录每次 MCP 工具调用（审计流：谁/工具/参数/结果/确认/时间）。
- AgentRun = 按 Step 聚合的"一次干活"记录（操作序列摘要、关联 Step、操作者）。
- **不做用户侧上报**（上报不可靠/可篡改、连接器扩展工作量大）。
- 用户侧 OpenClacky 对话/token 等执行详情不进 AgentRun。

### D10. 公共 Agent 分发 = 任务指令模式
- 连接器扩展静态内置**通用"CGC 助手"agent**。
- **Agent 定义存网站**（Agent 资源：prompt/skills/授权）；MCP 提供 `get_agent_instruction(workspace_id, agent_id)`。
- 用户说"用教研 Agent"→ 助手拉取定义 → 按定义工作。**公共 Agent 动态创建天然支持**。
- 不做运行时下发文件（热加载未验证、工程风险高）；不做纯静态打包（不支持动态公共 Agent）。

### D11. 工作区 Skill 同步到本地（源码验证可行）
- 工作区 Skill 定义存网站；经连接器扩展同步到本地 `~/.clacky/skills/`。
- 机制：`SkillLoader#create_skill / delete_skill` 运行时写文件 + 立即注册（已源码验证）；扩展 API handler 经 `@http_server` 访问 `@skill_loader`（与 session_manager 同模式）。
- 角色过滤在**网站侧**（扩展只拉到该用户角色可见的技能）。
- 触发：扩展静态打包 `cgc-sync` skill / aside 面板按钮。

### D12. 多工作区 Scope = 无状态 workspace_id
- **决定性事实**：OpenClacky 的 MCP client 是 server 级全局长连接（`@clients = {name => Client}`，进程级共享）→ 不能存服务端会话状态（会跨会话串）。
- 设计：所有 MCP 工具带**必填 `workspace_id`**（无状态、每调用鉴权 + 审计）。
- "当前工作区" = 对话上下文，由 CGC 助手维护（`get_workspace_context(workspace_id)` 定向，返回角色/可见 Agents/Skills/Steps）。
- Skill 本地同步加**工作区前缀** `cgc2046-<ws>-<skill>` 防多工作区撞名；网站生成 Agent 指令时引用带前缀的本地技能名。
- 不做"每工作区一个 MCP server"（工具名合并冲突）。

### D13. Onboarding = 一次性三步
1. **装 OpenClacky**（网站给安装命令）
2. **添加 MCP 连接**（粘贴 mcp.json 片段：`{type: http, url: https://cgc.example.com/mcp, headers: {Authorization: Bearer <token>}}`；token 从网站"连接设置"生成，绑用户不绑工作区）
3. **安装连接器扩展**：`openclacky ext install <zip URL>`
- **单一配置点 = mcp.json**：扩展自动读 mcp.json 的 cgc 条目拿 URL + token（零额外配置）。
- 加入新工作区无需重新配置（token 通用，scope 靠 workspace_id）。
- 不做"一条命令全自动"（扩展不代写 mcp.json，避免被覆盖）。

### D14. 连接器扩展命名 = `cgc-2046`
- 扩展 id：`cgc-2046`；MCP server 条目名沿用 `cgc-2046`；本地技能前缀 `cgc2046-<ws>-<skill>`。

## 本轮追加：Workflow 引擎与 8 角色旅程决策（D-A 系列）

> 日期：2026-08-01（晚间追加）· 依据：`docs/04-引擎验证/workflow-engine-ddd-design.md`（Jido/Workflow架构研究员与用户逐点讨论达成共识）
> 范围：workflow-first 架构 + 8 角色旅程定稿。保留 D1–D14，本系列为新增/修订决策。

### D-A1. workflow-first + Jido 生态架构

- **WorkflowDefinition（蓝图）/ WorkflowRun（执行实例）为 workflow 核心模型**；Step 四分类（自动 / 人工 / 门控分支 / 子 workflow）。
- 引擎选型 **Jido（Elixir）**：Action / Signal / Directive / Strategy / Agent 五件套 + **jido_runic**（DAG workflow 桥）+ **ash_jido**（Ash Resource action → Jido Action 桥）。
- **Runic 官方 `~> 0.1.0-alpha` 实验期——接受**：v1 锁版本 + 写适配层隔离，未来可替换自研 DAG 或升级稳定版。
- 落地形态：业务 context 定义"我能做什么（Action）/ 我关心什么（Signal）"，workflow 编排"何时做、按什么顺序"。

### D-A2. 教研与学习两个独立 workflow

- **Tutor 教研 workflow**（定义一次）→ 被 Event/Course **实例化复用** → **Learner 学习 workflow** 执行。
- WorkflowDefinition 带版本管理：改定义不影响已开始 run。

### D-A3. 8 角色旅程定稿

- **Learner**：
  - **Q1 事件级报名**——报名 = Enrollment（事件级参与者），与成员关系两类并存，**不自动成为 Workspace 成员**。
  - **Q2 BYO 全链路数字化**——报名/学习/答疑全在 Learner 自己的 OpenClacky，经 Signal 与平台通信。
  - **Q3 轻量表单 + 全免费**——报名不收费、不强制加入 Workspace。
- **Tutor**：教研 workflow 产出大纲/材料，现场辅导（答疑步骤）。
- **Volunteer**：**Workspace 长期成员**（非事件级参与者），被 Owner 指派到 Event 支持任务。
- **Owner**：筹备活动/开课程 = **跨角色 workflow**；**单步 CRUD 用表单**（单条增删改不进 workflow）。
- **Sponsor**：**Event + Workspace 两级赞助**，以账号参与赞助 workflow，不必成为成员。
- **Speaker**：**Event 级被邀请**（SpeakerInvitation），分享完关系结束，不成为成员。
- **Admin**：平台级；**Workspace 创建 = 申请审批 + 主动创建两级**。
- **Visitor**：**公开浏览**，**报名时注册登录**。

### D-A4. Enrollment 归活动 context

- Enrollment（事件级参与者）**归活动 context**，由报名 workflow **同步调 `create_enrollment` Action** 创建（强一致：名额/唯一性），**不自动成为 Workspace 成员**。
- 成员（WorkspaceMembership）与参与者（Enrollment）两类关系并存。

### D-A5. Workspace = partition 多租户 + Thread journal 审计

- **Workspace = 组织单元**（如"北京 CGC 分会"）= **一个 Jido partition**（registry identity / persistence / lineage / telemetry 隔离）；WorkflowRun 归属 partition。
- **审计 context 数据源 = Jido Storage Thread journal**（append-only + Checkpoint + Introspection 溯源链），不另造轮子。

### D-A6. 跨 context 同步 8 / 异步 2

- **同步直接调 Ash Action（强一致）为主（8）**：业务核心状态的主写入口，写完立即可读/约束检查。例：报名 workflow 最后一步创建 Enrollment。
- **发 Signal 异步最终一致（2）**：衍生副作用 / 跨 context 通知。例：`enrollment.completed` → 赞助权益更新、通知志愿者、触发学习 workflow。
- 理由：先把报名/开课主链路做稳；通知与衍生动作走信号，松耦合、可扩展。

### D-A7. J0 简化：BYO 引导三步（扩展自动配置 mcp.json）

- **三步 = 装 OpenClacky → 装扩展 → 扩展自动检查并安装 MCP（扩展负责自动配置 mcp.json，网站只生成 token）**。
- **取代 D13 步骤 2** 的"手动粘贴 mcp.json 片段"；保留"单一配置点 = mcp.json"与"token 绑用户不绑工作区"。
